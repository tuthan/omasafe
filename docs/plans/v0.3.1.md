# v0.3.1 — posture delta fields and exact capability counts

Five additive changes the OmaSafe panel's v0.3.1 release asked for, plus two defects
found while confirming them. Paired with plugin `0.5.0`, which already ships the
consuming code **dark**: every field below is optional, the panel renders nothing when
it is absent, and no panel change is required for the CLI to land these.

Source of the asks:
[`omasafe-plugin/docs/v0.3.1-plan.md` §5](../../../omasafe-plugin/docs/v0.3.1-plan.md)
and `omasafe-plugin/docs/design/08` §8 (C1, C2, C3, C5).

Effort **S · 1–2 days**. Risk: low everywhere except C1/C2, which change the persisted
posture state file and therefore need a migration that cannot lose an open coverage
episode.

## 1 Why the panel needs these

The panel is a renderer: it prints the state word the CLI assigns and never re-derives
one. That contract is what makes these CLI changes rather than panel changes.

Two of them unblock a surface that is already built and shipping dark. The panel can
render "changed from `pass`" on a check and `open 6 days` on a coverage gap today; it
renders neither, because no field carries the data. The plugin's own acceptance for that
work is explicitly **open** until a real two-run sequence on a changed host produces at
least one delta mark.

## 2 C1 — `checks[].previous_state`

**Field.** `string | null` on each check in `omasafe.posture.v1`. The state this check
held in the immediately preceding completed report. `null` on the first observation of a
check — **not** the current state, and never omitted-as-equal.

### The trap, confirmed live

`PostureState.previous_states` **is not the previous states.** `update_state()`
(`crates/omasafe-posture/src/lib.rs:579`) does

```rust
let prior = state.previous_states.insert(check.id.clone(), check.state);
```

The displaced prior value is bound to `prior`, used only to suppress duplicate coverage
notifications, and the map is overwritten with the **current** state before the file is
written. Verified against this host's live state file: `previous_states` holds
`boot.secure_boot: informational`, `encryption.root_luks: pass` — today's report,
exactly.

Exporting that map verbatim would make `previous_state == state` for every check
forever. The panel would render **zero** delta marks, and an absent mark reads as
"nothing changed" — a false quiet, which is the failure mode GR3 exists to prevent. It
would also pass the panel's synthetic fixture, because that fixture is deliberately
all-equal apart from one check; only a real two-run sequence catches it.

### Change

- `PostureState` gains `#[serde(default)] pub prior_states: BTreeMap<String, CheckState>`.
  `serde(default)` is the whole migration: an older state file loads with an empty map
  and the first scan after the upgrade populates it.
- `update_state()` captures the displaced value it already binds:

  ```rust
  match state.previous_states.insert(check.id.clone(), check.state) {
      Some(prior) => { state.prior_states.insert(check.id.clone(), prior); }
      // First observation of this check: no prior state exists, and `null` must mean
      // that rather than "unchanged".
      None => { state.prior_states.remove(&check.id); }
  }
  ```

- `CheckResult` gains `previous_state: Option<CheckState>`, always serialised (null when
  absent), and the report is annotated from `prior_states` **after** `update_state()` has
  run, so the value written to `posture-report.json` is the state from the preceding
  report. `posture export` then needs no state access at all: it returns the persisted
  report unchanged.

**Ordering matters.** `update_state()` must run before the report is written, which is
already the order in `posture()` (`main.rs:9057-9062`).

## 3 C2 — `checks[].gap_open_since`, and the `started_at` format defect

**Field.** RFC-3339 `string | null` on each check. When this check's current
`incomplete`/`error` episode began; `null` when the check is not in a coverage gap.
Sourced from `PostureState.coverage_episodes[id].started_at`, which is already genuine
first-seen data.

### The defect

This host's live state file:

```json
"started_at": "1788872597",  "last_seen_at": "2026-09-09T05:00:15Z"
```

Same object, same `String` type, two different formats — so the type system does not
catch it. Current code writes `started_at: now.clone()` where `now` is
`report.generated_at` (RFC-3339), so **new episodes are RFC-3339 and pre-existing ones
are bare unix seconds**. The field is mid-migration and nothing is migrating it.

Exporting it as-is would emit an unparseable timestamp for every episode that predates
the fix. (The panel degrades safely — `gapAgeText()` renders nothing on an unparseable
value — but "renders nothing" is not the intended behaviour for a gap that really is six
days old.)

### A second defect: a reopened gap inherited the earlier episode's date

`update_state` only cleared `coverage_episodes` on its third branch (pass,
informational, not applicable). `Attention` and `Regression` fell into the second
branch, which notifies and returns, so an `Incomplete → Attention → Incomplete`
sequence left the first episode parked in state and `or_insert_with` then kept its
original `started_at`. A gap that reopened on 9 September after recovering on 2
September reported itself as open since 1 September.

That was invisible while episodes were internal — they only keyed notification
suppression — and exporting `gap_open_since` turned it into a wrong date on screen. The
parked episode also carried `notified: true` across the recovery, so the reopened gap
was silently **not** notified.

An episode ends when observation RECOVERS, whatever state it recovers into: `Attention`
and `Regression` are observations that succeeded and reported something, not gaps. The
branch is restructured so the removal happens for every non-coverage-loss state.

### Change

- Normalise on load, so the state file self-heals on the next write rather than
  requiring every reader to handle both shapes: in `load_state()`, a `started_at` that
  parses as a bare integer is converted with the existing `format_timestamp()`.
  `timestamp_seconds()` and `format_timestamp()` already exist in the crate.
- `CheckResult` gains `gap_open_since: Option<String>`, annotated from
  `coverage_episodes` in the same pass as C1, and only for checks whose state
  `is_coverage_loss()`.

## 4 C3 — `checks[].catalog_index`

**Field.** `integer | null`. The check's stable position in `check_catalog()`.

The plugin's plan lists this as optional because the panel can fall back to sorting by
id. It should not be optional, and the reason only becomes visible from this side:
`check_catalog()` (`lib.rs:472`) is an ordered `Vec` whose order is deliberate and **not
alphabetical** —

```
host.context · updates.repository · updates.omarchy · vulnerabilities.arch_audit
· encryption.root_luks · firewall.configuration · firewall.service · firewall.effective …
```

— and because no index is exported, the panel sorts by id and draws its check strip in
alphabetical order. **The CLI's own reading order is being discarded at the boundary.**

**Change.** `scan()` sets `catalog_index` from the check's position in `check_catalog()`.
It is static catalog data and needs no state. The panel already prefers the index
whenever *every* check carries one, and ignores a partial index rather than interleaving
two orderings.

## 5 C5 — `review_summary.capabilities.by_class`

**Field.** `{ <class>: {total, emitted, omitted} } | null` on `omasafe.report.v1`,
mirroring the `findings.by_rule` block that already exists
(`main.rs:8564-8584`).

`analysis.capabilities[]` is scanner-selected and capped again by the panel, so a class
whose every instance was dropped is simply absent from the panel's grouping. Without a
per-class aggregate the panel cannot tell "this class was not observed" from "this
class's instances were dropped", so under any omission it marks every unobserved strip
position `–`, prefixes the counts `at least`, and titles the section `CAPABILITIES ·
PARTIAL`.

That presentation is correct, and pessimistic. `by_class` removes the pessimism: with an
exact per-class aggregate the strip can distinguish the two and print exact counts.

**Change.** Build `by_class` alongside `by_rule`, over capability class instead of rule
id, from the same pre-selection collection.

## 6 D1 — pending updates are `attention`, not `regression`

Not a panel ask; found while reading this crate for C1.

| assigned `Regression` | assigned `Attention` |
|---|---|
| `updates.repository` — packages behind (`:901`, `:959`) | `encryption.root_luks` — no disk encryption |
| `updates.omarchy` — omarchy behind (`:1066`, `:1254`) | `firewall.service` — no firewall running |
| `vulnerabilities.arch_audit` — known CVEs (`:1453`) | `kernel.restart` — running kernel ≠ installed |
| `execution.path` — world-writable PATH (`:1923`) | |

No disk encryption is `attention` while a pending package update is `regression`. And
`kernel.restart` (installed ≠ running) is `attention` while `updates.repository`
(available ≠ installed) is `regression` — the same shape of fact one step apart in the
same pipeline.

There is a second argument that only exists once C1 lands: **`regression` is the only
state word that asserts a comparison with a previous observation**, and until now the
report has carried none. Reserving it for checks that genuinely regressed, and letting
`previous_state` carry the comparison, makes the word mean what it says.

**Change.** `updates.repository` and `updates.omarchy` assign `CheckState::Attention`.
`vulnerabilities.arch_audit` and `execution.path` keep `Regression`: a known CVE and a
world-writable PATH entry are defects, not pending maintenance.

`CheckState::is_non_passing()` already groups `Regression | Attention | Incomplete |
Error`, so notification and exit-code behaviour are unchanged. Panel impact is
presentational only: the attention count is unchanged, the mark goes amber→yellow, and
the row sorts below `incomplete` in the panel's attention order.

## 7 Acceptance

**Unit, in `crates/omasafe-posture`:**

1. Two successive `update_state()` calls where a check's state changes produce
   `prior_states[id] == the first state`, and the report annotated from it carries that
   value as `previous_state` — **not** the current state.
2. A check seen for the first time has no `prior_states` entry and exports
   `previous_state: null`.
3. A check whose state is unchanged across two reports exports a `previous_state` equal
   to its state, and the panel renders no mark for it — this is the shape the trap
   produces for *every* check, so it must be reachable deliberately and must not be the
   only case tested.
4. A state file carrying `started_at: "1788872597"` loads with that episode's
   `started_at` normalised to `1986-09-08T…Z` shape, and an already-RFC-3339 value is
   left untouched.
5. `gap_open_since` is set only for checks in a coverage-loss state and is `null`
   otherwise; a continuing gap keeps its original start across scans and across an
   `Incomplete → Error` transition, while `Incomplete → Attention → Incomplete` starts a
   NEW episode dated to the reopening and notifies again.
6. Every check in `scan()` carries a `catalog_index`, and the indices are exactly
   `0..check_catalog().len()` with no gaps or duplicates.
7. `updates.repository` and `updates.omarchy` report `Attention`;
   `vulnerabilities.arch_audit` and `execution.path` still report `Regression`.

**Integration, on this host — the acceptance the plugin cannot close on its own:**

8. `posture scan` → change one observable condition → `posture scan` again → the affected
   check's `previous_state` differs from its `state`, and **no other check reports a
   differing `previous_state`**. This is the two-run sequence the plugin's T10 is blocked
   on. Passing only the synthetic fixtures would let the trap through undetected.

**Compatibility:**

9. An older `posture-report.json` with none of the new fields still loads and exports.
10. The plugin at `cliVersionMin: 0.3.0` renders identically against a 0.3.0 report and
    a 0.3.1 report that carries the new fields as null.

## 8 Out of scope

- `changes: { changed, first_observation }` — proposed as a convenience so the panel
  could print a one-line summary without walking `checks[]`. The panel walks the array
  and derives it in one pass; a second, redundant aggregate is a second thing to keep
  consistent.
- Retaining N previous reports for a posture history or state timeline. That needs a
  retention policy, a size bound, and a privacy review of what a posture history
  contains. Target 0.4.
- Any change to the check catalog itself: no checks added, removed or renamed, and
  `CHECK_CATALOG_VERSION` stays `1`. C3 exports the order that already exists.
