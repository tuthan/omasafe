# v0.2.3 Persistent Scan Snapshot Implementation Plan

Status: implementation complete; release gates pending clean-VM access · 2026-09-04 · Owner: Hung Vo · Scope source:
maintainer-requested persistent caching of the last successful installed-plugin scan

This release makes the last successful installed-plugin scan available after an Omarchy Shell
restart without treating old data as a fresh security result. The CLI persists a bounded,
normalized snapshot under its existing XDG cache directory; the plugin asks the CLI to read and
validate it and never owns cache files, schemas, permissions, or compatibility decisions.

The current plugin already writes a parsed `omasafe.scan-cache.v1` document from
`BarWidget.qml`, but that implementation duplicates the CLI's XDG logic, compares producer CLI
versions exactly, has no inventory or wider scan-context identity, and relies on QML file-writing
semantics for privacy. v0.2.3 replaces that implementation rather than layering a second writer
onto `${XDG_CACHE_HOME:-~/.cache}/omasafe/last-scan.json`.

The cache implementation is decomposed into vertical slices `K0`–`K3` and `K5`; `K4` tracks an
independent agent-skill hotfix that ships first. Each slice ends committed and verified per
[`../progress.md`](../progress.md). Cache-bearing slices preserve the earlier snapshot on every
failed or incomplete scan, and the release leaves existing v0.2.2 scan, notification, and
enforcement behavior working end to end.

## Outcome

On shell startup, an operator who has a compatible successful scan snapshot sees a state such as:

```text
Cached · scanned 2 hours ago
```

The cached provenance and age remain visible. The snapshot begins as unvalidated/stale; a
read-only CLI validation may confirm that all result-affecting inputs still match, but it never
changes the historical generation time or presents the data as a newly executed scan. A fresh
successful scan replaces the matching profile snapshot. A failed, timed-out, interrupted,
overflowed, malformed, or otherwise incomplete scan leaves the earlier snapshot byte-for-byte
available and the UI says that the latest attempt failed while showing the older cached result.

The persisted document contains only the normalized alert set, enforcement summary, identities,
timestamps, profile, and validity metadata required by consumers. Raw stdout, raw stderr, full
analysis reports, payload inventories, source excerpts, and transient process errors are never
stored in this cache.

## Strategy Decisions

1. **The CLI is the sole cache authority.** `omasafe-cli` creates the directory, constructs the
   snapshot from typed scan data, writes it atomically, reads it with a byte bound, decides schema
   and producer compatibility, and validates current context. QML neither opens nor writes the
   cache file and does not reproduce compatibility or fingerprint logic.
2. **The cache is an acceleration artifact, not audit state.** Snapshots live below
   `${XDG_CACHE_HOME:-~/.cache}/omasafe/` and may disappear at any time. Trust history,
   enforcement history, overrides, suppressions, notification deduplication, and review records
   remain under XDG state/config and never depend on the snapshot for correctness.
3. **Cache typed results, never process streams.** The CLI builds a snapshot from the same typed,
   semantically validated `ScanResult` that feeds the report. It does not capture or reparse its
   own stdout, and no consumer persists stdout/stderr after the process exits.
4. **Inventory identity is necessary but not sufficient.** The snapshot stores a versioned
   `inventory_fingerprint` and a broader versioned `scan_context_fingerprint`. Context covers
   every local input that can change alerts or enforcement presentation: trust/exclusion state,
   marketplace snapshot identity and age boundary, analyzer policy, enforcement history/policy,
   relevant override expiry, supported-runtime identity, and scan profile.
5. **Cached provenance stays visible after validation.** Startup hydration is always labelled
   `Cached`. Before validation it is stale with reason `unvalidated`. A successful context check
   may change the validity state to `valid`, but it does not change `generated_at`, claim that a
   scan just ran, or erase the cached label and age.
6. **Compatibility is schema-driven, not exact-version equality.** The snapshot records the
   producer CLI version for provenance. The reader accepts only cache/report/fingerprint schemas
   it explicitly understands and applies a documented producer compatibility rule. A harmless
   patch-version change alone does not invalidate a snapshot; an incompatible schema or semantic
   contract does.
7. **Profiles never overwrite one another.** At minimum, `installed-basic` and
   `installed-analysis` use separate snapshot paths. A basic advisory schedule cannot erase a
   richer analysis snapshot, and the widget requests the exact `installed-analysis` profile it
   renders. Under hardened scheduling, timer and widget intentionally share `installed-analysis`;
   same-profile replacement is allowed only through monotonic generation ordering. Unknown profiles
   fail closed.
8. **`--only-new` is presentation, not cache content.** Scan collection builds one complete,
   normalized live-alert set before `--only-new` filters terminal output or notification work.
   The profile cache always receives the complete set. The historical count of alerts considered
   new may be reported as `new_at_generation`, but it is not used as current newness after
   hydration or context validation.
9. **Exit `0` and exit `3` are successful scan outcomes.** Exit `3` means actionable findings,
   not an operational failure. Both may replace a snapshot after the complete typed result and
   enforcement summary validate. Every other exit and every pre-result failure leaves the cache
   untouched.
10. **Atomicity includes concurrency and durability.** A profile-specific lock serializes cache
    replacement. A unique `create_new` temporary file is written with mode `0600`, flushed,
    renamed within the same directory, and followed by a parent-directory sync where supported.
    An older generation may not replace a newer snapshot even if concurrent scans finish out of
    order. Ordering uses a profile-local generation reservation allocated before scan work; it does
    not rely on `generated_at` wall-clock ordering, which is ambiguous across equal timestamps and
    clock rollback.
11. **Private permissions are mandatory.** The CLI enforces `0700` on the OmaSafe cache
    directory and `0600` on snapshot and lock files. This is required even though current compact
    alerts usually omit paths, because future findings may contain local path or plugin identity
    details. Permission repair and restrictive creation are tested under a permissive umask.
12. **Persistence failure is separate from scan validity.** If a valid scan cannot be cached,
    the live scan result still succeeds with its normal exit `0` or `3`; the report and UI expose
    a bounded cache-persistence warning. The previous snapshot is retained. Cache failure never
    mutates security state or turns findings into an operational scan failure.
13. **Login hydrates but does not validate.** Shell startup runs only the bounded `show` request and
    presents compatible data as cached-unvalidated. The inventory/content/Git validation pass is
    deferred until first panel open or satisfied by a subsequent periodic/manual full scan, avoiding
    N-plugin work and routine state-lock contention on the login critical path.
14. **Validation reads state without recovering it.** It may create or repair a private lock file as
    synchronization metadata, but never quarantines, renames, resets, rewrites, or acknowledges
    state. Shared-lock contention and malformed state are bounded status results, not destructive
    recovery opportunities.

- Approve profile-separated snapshots, with the v0.2.3 widget consuming

  from `plugins inventory` but not from `ScanResult`.

  `last-scan.json`, avoiding mixed old/new writers during a plugin/CLI version-skew window.

- Approve cache persistence before terminal rendering, with an additive bounded persistence-status
  field selected before the report is serialized and printed.
- Approve login-time hydration without validation; defer the bounded validation pass to first panel
  open or reuse the result of a later periodic/manual full scan.
- Approve lock-file creation/mode repair as the only synchronization-metadata carve-out from
  read-only validation; state documents and corrupt inputs are never quarantined or rewritten.

  separately planned candidate-acquisition release.

## Snapshot Contract

### Paths and profiles

CLI-owned snapshots live at:

```text
${XDG_CACHE_HOME:-$HOME/.cache}/omasafe/scan-snapshots/installed-basic.json
${XDG_CACHE_HOME:-$HOME/.cache}/omasafe/scan-snapshots/installed-analysis.json
```

Each profile also has a fixed, bounded private generation-reservation file in `scan-snapshots`.
Its unsigned counter is allocated under the same profile lock before scan work. The filename is
selected by the closed profile enum, never by caller text; a missing file starts at generation one,
while malformed data or overflow disables replacement for that run and produces a cache warning.

The filenames are fixed by a closed profile enum, never derived from caller-controlled text. The
legacy QML-authored `${XDG_CACHE_HOME:-$HOME/.cache}/omasafe/last-scan.json` is not imported,
rewritten, or treated as trusted input. The updated plugin stops reading and writing it. A normal
CLI path initialization still repairs the parent OmaSafe cache directory to `0700`, protecting a
legacy orphan until the user or a later explicit cleanup removes disposable cache data.

`installed-basic` represents `scan` without analysis. `installed-analysis` represents
`scan --include-analysis`. `--notify`, `--only-new`, output format, and text/JSON rendering do not
create profiles because they must not change the canonical live result.

### Versioned document

The stored JSON is a private CLI cache contract, distinct from the public report envelope:

```json
{
  "schema": "omasafe.scan-snapshot.v1",
  "report_schema": "omasafe.report.v1",
  "producer_cli_version": "0.2.3",
  "generation": 42,
  "generated_at": "2026-09-04T12:00:00Z",
  "valid_until": null,
  "scan_profile": "installed-analysis",
  "inventory_fingerprint": {
    "schema": "omasafe.inventory-fingerprint.v1",
    "digest": "<lowercase sha256>"
  },
  "scan_context_fingerprint": {
    "schema": "omasafe.scan-context.v1",
    "digest": "<lowercase sha256>",
    "components": {
      "inventory": "<lowercase sha256>",
      "trust": "<lowercase sha256>",
      "marketplace": "<lowercase sha256>",
      "analysis_policy": "<lowercase sha256>",
      "enforcement": "<lowercase sha256>",
      "runtime": "<lowercase sha256>"
    }
  },
  "alerts": [],
  "new_at_generation": 0,
  "enforcement_summary": {
    "schema": "omasafe.enforcement-summary.v1",
    "available": true,
    "decisions": []
  }
}
```

Exact nested schema strings reuse the released constants where they already exist. The example
does not authorize renaming an existing enforcement schema merely to match the illustration.

The reader applies a fixed maximum UTF-8 byte size before allocation and deserialization. It
rejects duplicate JSON keys, missing required fields, non-finite/negative counts, unknown profile
or required enum values, malformed timestamps, timestamps implausibly in the future, malformed
digests, an alert count above the documented bound, and enforcement summaries whose required
schema is unsupported. Unknown additive fields may be ignored only where that behavior is stated
by the schema. The same pre-allocation discipline applies to every manifest and state document read
to construct or validate the context; a small cache file does not bound its transitive inputs.

### Normalized alerts and summaries

Each cached alert contains a stable alert key plus the existing bounded presentation fields:

```text
CachedScanAlert {
    key,
    plugin_id,
    kind,
    severity,
    reason_code,
    message,
    post_change,
}
```

Coverage/unavailable alerts use a closed stable `reason_code`. Their cached `message` is selected
from a fixed bounded code-to-copy table; raw child-process, parser, filesystem, and joined
limitation error strings remain bounded live diagnostics and are never snapshot content.

The key is the same stable identity used by scan-state deduplication, not a hash of mutable prose.
Alerts are deduplicated by key and sorted by a documented tuple such as severity rank descending,
then plugin ID, kind, and key. Normalization occurs before both cache serialization and public
report rendering so a valid snapshot cannot disagree with the live result merely because of
filesystem walk order.

`quiet`, `outstanding`, blocked-decision count, and highest severity are derived from the
normalized alert set and enforcement summary when read. If retained in the public report for
backward compatibility, they are not independently trusted from cache bytes. `new_at_generation`
is historical metadata only; hydration does not paint old alerts as newly detected.

The canonical `scan` result gains the same typed enforcement summary currently calculated for
`plugins inventory`. A missing or corrupt enforcement history produces the existing explicit
`available: false` summary and corresponding limitation; it never silently becomes an empty,
available decision list.

## Fingerprint and Validity Contract

### Inventory fingerprint

The inventory fingerprint hashes a domain-separated canonical serialization of the installed
targets and inventory-wide coverage facts that affect scan output. Records are sorted and include,
where applicable:

- plugin ID, classification, enabled/active/full-bar state;
- repository, head, tree, relevant-content digest, file count, and identity limitations;
- duplicate/unscannable/backup classification needed by scan semantics;
- shell-inventory availability and normalized coverage limitations; and
- active full-bar replacement/conflict facts.

Only the final digest and schema are stored. Canonical fingerprint material is not written to the
snapshot, preventing the fingerprint section from becoming a second path/inventory disclosure.

### Scan-context fingerprint

The context fingerprint binds the inventory fingerprint to other result-affecting inputs:

- latest applicable trust baselines, acknowledgements, revocations, and exclusions;
- verified marketplace snapshot repository commit, file digest, retrieval time, verification
  state, and the time at which its age crosses the scan's stale threshold;
- analyzer policy identity for `installed-analysis`, or a fixed not-applicable marker for
  `installed-basic`;
- enforcement history/summary schema and applicable decisions;
- enforcement-policy identity and active override bindings where they affect the rendered
  summary, including their earliest expiry;
- the CLI-declared supported runtime contract from the existing
  `provenance.supported_runtime.omarchy` and `.quickshell` fields; and
- the closed scan-profile value and fingerprint schema versions.

For `installed-analysis`, `PolicyIdentity.supported_surface_version` remains part of the analyzer
policy component rather than being duplicated in runtime. v0.2.3 does not invent an installed-shell
probe: the runtime component identifies the compiled support contract and changes only when those
named provenance fields change.

Components use canonical JSON with sorted object keys and sorted set-like lists, prefixed by a
domain/version string before SHA-256. Each component digest is stored so validation can return a
bounded stale reason such as `inventory-changed`, `trust-changed`, `marketplace-changed`,
`analysis-policy-changed`, `enforcement-changed`, `runtime-changed`, or `expired`, without exposing
the underlying path or record. `context-changed-during-validation` is returned when pre/post
observation witnesses differ; a digest assembled across that race is never accepted.

`valid_until` is the earliest known instant at which a currently matching context can become
invalid solely through time: override/suppression expiry where applicable, marketplace staleness,
or another released time-bound input. Validation after that instant returns stale even if every
stored digest still matches. A null value means no known time-only boundary, not that the cache is
permanently fresh.

### Consumer states

`scan-cache show` returns one of these closed states:

| State | Snapshot included | Meaning |
|---|---:|---|
| `missing` | no | No snapshot exists for the requested profile. |
| `cached-unvalidated` | yes | Compatible snapshot loaded; always stale until checked. |
| `cached-valid` | yes | Current context and time bounds match; provenance remains cached. |
| `cached-stale` | yes | Compatible snapshot loaded, but one or more bounded stale reasons differ. |
| `incompatible` | no | Cache/report/fingerprint/profile/producer contract is unsupported. |
| `corrupt` | no | Bytes violate the bounded snapshot schema. |

`show` without `--validate` never computes current inventory/context and therefore never returns
`cached-valid`. `show --validate` is read-only with one narrow synchronization carve-out: it may
create or repair a private lock file, but it collects and hashes the current context without running
analyzer detectors, sending notifications, changing state-document contents, quarantining corrupt
state, or replacing the cache. It may be materially cheaper than `scan --include-analysis`, but it
remains bounded and timed. Shared-lock contention returns `cached-unvalidated` plus
`state-lock-busy`; malformed or unreadable state returns a named limitation and
`state-input-invalid`. Both use exit `0` when the compatible snapshot itself was read successfully.
Validation performs one inventory/source collection, uses only capped child processes and bounded
non-quarantining state/manifest reads, and takes state snapshots under short ordered shared-lock
windows rather than holding locks during tree hashing.

Missing, incompatible, corrupt, lock-busy, and invalid-state results are expected status results
rather than top-level usage errors. Operational inability to inspect the XDG path itself uses exit
`1`. No state allows incompatible snapshot alerts to reach QML.

## CLI Surface

Regenerate the man page and completions through `scripts/generate-cli-assets.sh` after updating
`docs/cli-surface.txt`.

```text
scan [--format text|json] [--notify] [--only-new] [--include-analysis]

scan-cache show
    [--profile installed-basic|installed-analysis]
    [--validate]
    [--format text|json]
```

The default cache profile is `installed-analysis` because the interactive widget has invoked
`scan --include-analysis` since v0.2.1. Callers should still pass the profile explicitly. There is
no cache `write`, `import`, `clear`, `trust`, or `mark-current` command in v0.2.3.

The JSON response uses the normal `omasafe.report.v1` envelope and a new typed result schema that
contains `state`, `stale`, `stale_reasons`, profile, cache generation age inputs, optional snapshot,
and bounded limitations. Every response identifies the profile and generation it describes; when no
compatible snapshot exists, generation and snapshot are both absent. Cache bytes are nested only
after compatibility and structural validation.
Text output never prints alert messages by default; it prints the state, profile, generation time,
and stale reasons.

## Replacement and Failure Semantics

A snapshot candidate becomes eligible only after:

1. inventory collection and all requested analysis complete within their existing bounds;
2. the canonical full alert set is normalized independent of `--only-new`;
3. the enforcement summary and every required fingerprint component are available or represented
   by an explicit covered limitation allowed by the scan contract;
4. the typed cache snapshot and both bounded public-report persistence-status variants serialize
   within their respective byte bounds;
5. scan outcome is the normal quiet result (`0`) or actionable result (`3`); and
6. its profile-local generation was reserved before scan work and, under the profile lock, is newer
   than the currently stored snapshot.

The CLI briefly takes the profile lock before scan work to reserve the next private monotonic
generation, without relying on the wall clock or holding the lock during collection. It later
creates a unique temporary file in `scan-snapshots`, writes with restrictive mode, flushes the file,
renames it over the profile path, and syncs the parent directory where the platform supports it.
Every operation below the opened XDG cache anchor is directory-relative and no-follow; CLI-owned
objects must be owned by the effective UID. Temporary files are removed on handled failure. Startup
may clean only well-formed stale temporary names owned by the current user and older than a
conservative bound; it must never follow symlinks or recursively remove caller-selected paths.

These events do not replace or truncate the previous snapshot:

- inventory, history, marketplace, analysis, enforcement, serialization, lock, or write failure;
- malformed internal data or a result above the cache byte/count cap;
- timeout, interrupt, SIGTERM/SIGKILL escalation, output overflow, or exit other than `0`/`3`;
- a scan generation older than the stored profile snapshot; or
- a cache candidate whose declared profile does not match the invoked scan profile.

A cache-write failure after a valid scan is added as bounded report metadata/stderr diagnostic and
systemd-log evidence. It does not rewrite the result to `unavailable`, change alert severity, or
alter notification/enforcement state.

Persistence precedes terminal rendering. After the canonical result is complete, the CLI
pre-serializes the snapshot and the bounded success/failure report variants, attempts atomic
replacement, selects the additive typed `cache_persistence` status, then serializes/prints the public
result once. `cache_persistence` is public report metadata only and is never embedded in the
snapshot. The QML normalizer consumes known status values and, consistent with the additive v1
envelope contract, tolerates unknown additive result fields.

## Plugin Startup and UX Contract

After the existing CLI path and minimum-version probe succeeds, `BarWidget.qml` performs:

1. `scan-cache show --profile installed-analysis --format json` and, if compatible, immediately
   hydrates alert rows and enforcement badge state as stale `Cached` data;
2. no inventory, content-digest, Git, or validation collection on the login path; and
3. `scan-cache show --profile installed-analysis --validate --format json` only on first panel open,
   after the cached panel state has rendered, unless a subsequent periodic/manual full scan has
   already supplied a current result.

The validation request uses the same timeout, output cap, terminal-decision latch, argv-only
launcher, and CLI authorization gate as other plugin commands. It carries the profile and generation
it validated. A validity-only transition is applied only when both match the currently rendered
snapshot; a different complete response is normalized and replaces the prior response atomically.
A missing/incompatible/corrupt response likewise replaces the cache state rather than validating old
alerts. A late validation completion from an older widget/request generation is discarded.

Required copy/state examples:

```text
Cached · scanned 2 hours ago                 # loaded, validation pending/unavailable
Cached · validated · scanned 2 hours ago     # context confirmed; still visibly cached
Cached · stale: inventory changed · 2h ago  # context mismatch
Scan failed · showing cached result from 2h ago
No cached result                               # missing; does not claim no prior scan occurred
Cached result unreadable                       # corrupt; surfaced once, no alerts consumed
Cached result requires a compatible CLI        # incompatible; no alerts consumed
```

The exact compact wording may be shortened to fit, but must preserve cached provenance, age, and
staleness. A stale or cached quiet snapshot never uses an unqualified current green/no-alert claim.
Alert counts and rows may remain visible but use the existing stale/dim treatment. A fresh scan
failure does not clear hydrated alerts, enforcement summary, generation time, or profile; a fresh
success applies the live result and the subsequent CLI-owned snapshot without a QML write. Corrupt
cache is surfaced once per observed generation/file state rather than silently treated as
never-scanned or repeatedly notifying on every render.

The plugin removes:

- `cacheHome`, `scanCacheDir`, `scanCachePath`, and cache-ready/pending QML state;
- `scanCacheSnapshot`, `queueScanCache`, `flushScanCache`, `loadScanCache`, and direct cache
  compatibility logic;
- the `mkdir` process and cache `FileView`; and
- documentation claiming that the plugin stores the snapshot.

The plugin manifest raises the feature minimum to CLI `0.2.3`. An older plugin paired with the
new CLI may continue writing its legacy filename but cannot overwrite the new profile-separated
CLI snapshot. A new plugin paired with CLI `0.2.2` disables persistent hydration with a clear
upgrade explanation and retains manual scan behavior only if the existing overall compatibility
policy permits it.

## Security and Lifecycle Test Matrix

### Cache bytes and compatibility

- Empty, truncated, over-cap, invalid UTF-8, duplicate-key, deeply nested, wrong top-level type,
  missing-field, unknown-required-enum, invalid timestamp/digest, future timestamp, excessive-alert,
  and unsupported nested enforcement schema fixtures.
- Same patch-compatible producer, older supported producer, newer unsupported producer, incompatible
  report schema, incompatible fingerprint schema, and unknown profile.
- Legacy QML `omasafe.scan-cache.v1` at `last-scan.json` is never imported or displayed by the new
  cache command.
- Oversized manifest/trust/suppression/scan/enforcement/override inputs are rejected before full
  allocation; hanging or over-output fake `omarchy`/Git children time out and become limitations.

### Replacement and permissions

- New directory under umask `000`, `022`, and `077`; final directories remain `0700`, files/locks
  `0600`.
- Existing permissive directory/file, symlink at final/temp/lock path, non-directory parent,
  read-only filesystem, disk-full/short-write injection, rename failure, and sync failure.
- Symlink or rename substitution at the CLI-owned `omasafe` and `scan-snapshots` directories, plus
  a foreign-owned controlled descendant where the platform test harness permits changing UID.
- Concurrent writers for one profile and both profiles; an older generation never replaces newer
  data and readers observe either complete old or complete new JSON.
- Equal wall-clock timestamps, backward wall-clock adjustment, process suspension, generation
  reservation corruption/overflow, and out-of-order completion cannot regress or wedge replacement.
- Scan exit `0` and `3` replace; every other exit, timeout, interrupt, output overflow, internal
  validation failure, and cache-write failure retains the old bytes.
- Cache replacement completes before stdout rendering. Success and injected persistence failure each
  select the correct pre-bounded public `cache_persistence` variant, print once, and never alter the
  snapshot schema or leak attempt-local diagnostics into snapshot bytes.

### Fingerprint validity

- Relevant plugin byte/mode/identity change, add/remove/backup/unscannable transition, enabled or
  full-bar change, and shell-inventory coverage change.
- Trust/acknowledgement/revocation/exclusion change, marketplace commit/digest/verification/age
  change, analyzer policy update, a change to the pinned supported-runtime provenance fields,
  enforcement history/policy change, and time crossing `valid_until`.
- Reordered semantically identical inputs yield identical component and aggregate digests.
- Validation is read-only apart from creating or mode-repairing private lock metadata: state/config/
  cache path inventories and bytes before and after are unchanged, including for corrupt inputs; no
  quarantine file, notification, baseline, decision, acknowledgement, or scan-state mutation occurs.
- A writer holding either state lock beyond the bounded retry yields
  `cached-unvalidated`/`state-lock-busy` with exit `0`; malformed state yields
  `state-input-invalid` without rename/reset. A later uncontended validation can still succeed.
- Coordinated mutation between component reads or during plugin collection yields
  `context-changed-during-validation` after at most one retry and never `cached-valid`.

### Scan profiles and presentation

- Basic and analysis snapshots coexist; either order of completion preserves both.
- `--only-new` and full output produce the same cached normalized alert set for identical state.
- Notification delivery success/failure does not change the cached alert set or profile.
- Startup shows cached/stale without validation. First panel open may show cached/validated after a
  generation match or cached/stale with a named reason; missing says `No cached result`, while
  incompatible/corrupt states use distinct one-shot explanations and contribute no alerts.
- A failed new scan preserves rows, counts, enforcement block marker, generation time, and cached
  provenance while clearly surfacing failure.
- Fresh and cached envelopes with contradictory quiet/count/severity/enforcement aggregates,
  unknown required enums, invalid timestamps, non-finite/negative counts, excessive collections, or
  over-cap strings are rejected atomically; an earlier normalized result remains visible.
- Before first panel open, the panel loader has not constructed `Panel.qml`; first open is replayed
  after load and subsequent close/open preserves the documented state behavior.
- A snapshot replaced or deleted between `show` and `show --validate` never receives a cross-
  generation validity transition: matching profile/generation updates validity only, while a
  different generation or no-cache response replaces the normalized state atomically.
- An advisory fixture with recorded enforcement blocks activates the now-supported block badge for
  fresh and cached results; release copy identifies this as newly visible behavior.

### Agent skill v1.1.1 transport

- Local full and review-profile scans of the release plugin produce a bounded useful result; the
  review profile is never required to carry remote acquisition metadata.
- Request, Git, and marketplace candidate routes still require immutable acquisition identity,
  scan-only operation, candidate-unsuppressed policy, and valid omission arithmetic.
- A structured summary over budget preserves the documented bounded finding and coverage subset,
  exact total/emitted/omitted counts, and fingerprint; it sets `summary_reduced` without claiming a

- A high-severity finding or coverage limitation at each retention boundary is either present or

### Performance regression budgets

- `scan-cache show` reads at most the snapshot byte cap, walks no plugin directory, and spawns no
  `omarchy`, Git, analyzer, or notification process.
- `show --validate` performs one bounded inventory/source pass, one bounded read of each applicable
  state document, no analyzer pass, and no duplicated manifest read. Child count and bytes read are
  asserted with instrumented fixtures.
- A successful scan constructs its snapshot and component fingerprints from the same typed
  observation that produced the live result; cache persistence performs zero additional target-tree
  reads.
- The clean-VM fixture records cold/warm elapsed time and peak RSS for `show`, `show --validate`, and
  `scan --include-analysis`; thresholds frozen in K0 fail the release gate on an unapproved
  regression.
- Shell cold-start records time to first frame, child-process count, and retained RSS/object count
  before first panel open; cache hydration stays within budget, launches one CLI process with no
  inventory/Git grandchildren, and `Panel.qml` remains unloaded. Validation cost is charged to first
  panel open, not login.
- Agent runner fixtures record raw bytes, emitted summary bytes, wall time, and retained evidence;
  both normal review output and the reduction path remain below the 64 KiB transport contract.

## Risks and Mitigations

- **Inventory-only validation approves wrong alerts** → bind every result-affecting component in
  the scan-context fingerprint and include explicit time validity boundaries.
- **An advisory scheduled scan erases analysis results** → advisory writes `installed-basic`; the
  hardened timer intentionally shares `installed-analysis` with the widget and relies on monotonic
  generation ordering.
- **`--only-new` persists an incomplete view** → canonicalize/cache the full live set before
  presentation filtering.
- **Old QML and new CLI race on one file** → new profile-separated CLI paths; never reuse or
  migrate the legacy QML filename.
- **Version upgrades discard useful cache unnecessarily** → schema/semantic compatibility,
  producer version retained only as provenance where compatible.
- **Cache is mistaken for a fresh scan** → permanent cached label, generation age, initial stale
  state, and separate validation/full-scan transitions.
- **Findings expose local paths to other users** → `0700` directories, `0600` files/locks,
  restrictive create modes, mode repair, bounded content, and no raw streams/full analysis.
- **Concurrent scans tear or regress the snapshot** → profile lock, unique temporary,
  same-directory rename, sync, and a pre-scan monotonic generation reservation independent of wall
  time.
- **Validation hangs or allocates from unbounded transitive input** → cap manifests and every
  state document before allocation; bound shell/Git children by time and output; disclose loss.
- **Validation certifies a mixed old/new context** → short ordered state snapshots, mutable-input
  witnesses, one bounded retry, and a closed raced-context stale reason.
- **Validation collides with a timer/manual scan** → use short shared locks, return
  `cached-unvalidated`/`state-lock-busy` on bounded contention, and defer validation off login.
- **A later generation validates earlier rendered alerts** → bind every validity transition to both
  profile and generation; otherwise atomically apply the complete newer/no-cache response.
- **Read-only validation quarantines corrupt state** → use bounded non-recovering loaders and permit
  only private lock-file creation/mode repair as synchronization metadata.
- **Cache path components are swapped or foreign-owned** → anchored directory-relative no-follow
  operations, type/UID checks, and refusal before permission repair.
- **Caching adds a third plugin-tree read or hidden startup cost** → reuse the live typed
  observation, instrument child/read counts, and enforce the K0 performance budgets.
- **A malformed CLI response paints a false quiet state** → normalize fresh and cached responses
  through the same closed, bounded consistency checks before any QML state mutation.
- **The panel dominates cold shell startup despite cache optimization** → load it on first open and
  keep startup cache work small, sequenced, measured, and independent of the panel graph.
- **The agent transport reports counts but loses review evidence** → separate local/remote profile
  validation, retain a bounded evidence subset with exact omissions, and distinguish stream loss
  from summary reduction.
- **Persistence failure hides a valid result** → return the live result normally, retain old
  cache, and surface a separate bounded persistence warning.
- **Cache becomes hidden authoritative state** → no security decision reads it as input; cache
  deletion is supported and trust/enforcement/notification correctness remains under XDG state.

## Acceptance Criteria

- The CLI, not QML, is the only writer and validator of persistent scan snapshots.
- Snapshots contain cache/report/fingerprint schemas, producer CLI version, monotonic generation,
  generation time, profile, inventory and scan-context fingerprints, normalized full alerts, and
  enforcement summary.
- No snapshot contains raw stdout/stderr, full analyzer output, payload entries, source excerpts,
  transient process errors, joined raw limitations, or secret values; cacheable unavailable/coverage
  alerts use stable reason codes and fixed bounded copy.
- Startup hydration reads `Cached · scanned … ago`, is stale until validation, and remains visibly
  cached after a successful validation.
- Inventory and every other named scan-context change makes the snapshot stale; time-dependent
  state cannot remain valid past `valid_until`, and a context that changes during observation can
  never validate or become a persisted candidate.
- Compatible schema/producer combinations are accepted without exact patch-version equality;
  incompatible cache/report/fingerprint/profile versions never reach presentation.
- A valid scan with exit `0` or `3` atomically replaces only its matching profile snapshot after the
  canonical result is complete. Every failed/incomplete scan retains the earlier snapshot.
- `--only-new` never changes cached alert completeness, and a basic scan never overwrites an
  analysis snapshot.
- The cache directory is `0700`; snapshot, temporary, and lock files are created `0600` and remain
  private after replacement and mode repair. CLI-owned descendants are accessed from an opened
  directory anchor, never followed through symlinks, and must be owned by the effective UID.
- Every process and file reached by deferred validation has an enforced time/output/byte bound before
  allocation, and cache production performs no additional plugin-tree read beyond the live scan.
- Validation uses shared locks and non-quarantining loaders. Contention/invalid state are exit-`0`
  cached status results, and only private lock synchronization metadata may be created or repaired.
- Cache persistence failure is visible but does not change scan findings, severity, enforcement,
  notification behavior, or valid scan exit semantics. Persistence completes before terminal
  rendering, and its additive bounded report field never enters snapshot bytes.
- QML applies one strict normalization contract to live and cached CLI responses, preserves an
  earlier result through failure, rejects malformed/contradictory/excessive fields and unknown cache
  states/schemas/reasons, and has no direct cache filesystem access.
- A cache validity-only transition is applied only to the same profile/generation; a different
  generation or authoritative no-cache response replaces normalized cache state atomically.
- `Panel.qml` is not instantiated until first open. Login performs bounded `show` only; validation is
  generation-bound and deferred to first open or superseded by a newer full scan.
- The agent skill accepts local review profiles without acquisition metadata, preserves bounded
  security evidence and exact omissions under its summary cap, and never conflates summary reduction
  with raw-stream truncation.
- The agent-skill v1.1.1 fix for CLI v0.2.2 ships independently before the v0.2.3 cache tag; CLI,
  plugin, scheduled-scan, clean-VM, package-upgrade, determinism, corpus, self-scan, and release gates
  pass before tagging v0.2.3.

## Explicit Non-Goals

- Treating the cache as an audit log, baseline, trust record, acknowledgement, override, enforcement
  authorization, notification queue, or source of security decisions.
- Persisting plugin-analysis detail sheets, rule explanations, rule/coverage collectors, candidate
  source-scan results, raw reports, evidence excerpts, or complete payload inventories.
