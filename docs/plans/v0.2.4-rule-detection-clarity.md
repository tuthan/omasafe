## Outcome

The first review screen must answer:

1. Which exact bytes and analyzer were used, and is this fresh or cached evidence?
2. Which consequential behaviors were observed, and where is their evidence?
3. What producer, destination, execution argument, or trigger needs inspection?
4. Which relevant behaviors or payloads remain unresolved?
5. Were results suppressed or shortened, and was lifecycle policy evaluated?

Preserve capabilities, findings, coverage, and enforcement as separate facts.
A static connection is possible behavior, not proof of execution, intent, or
consent. An empty report is never a plugin safety verdict.

## Identity, Cache, and Migration Contract

### Full identity: automatic cache invalidation, package-local build inputs

Implement a small build helper in each of `omasafe-core` and `omasafe-analyzer`.
Each package hashes only its own `src/` runtime Rust files, excluding paths under
`tests/` or `golden/` and basenames ending in `_tests.rs`. Sort package-relative
paths and hash domain-separated, length-prefixed path/content bytes using SHA-256.
Inline tests, comments, and formatting in runtime files can conservatively change
this hash. That is suitable for cache invalidation, not automatic invalidation of
all users' review decisions.

Each package's `build.rs` includes its own `build_support.rs` with
`#[path = "build_support.rs"] mod build_support;`. Its integration test target
`tests/build_fingerprint.rs` includes the helper with
`#[path = "../build_support.rs"] mod build_support;` and exercises temporary
source trees. Add SHA-256 as a build dependency as well as the test dependency
where needed. Track traversed directories/files with `cargo:rerun-if-changed`,
including additions/removals; track the build script/helper too. Explicitly include
these helper files in package contents. Test each package from a extracted source
layout without its sibling's source directory; provide dependencies through normal
Cargo resolution/local test configuration, not relative source-file reads.

Core exports its generated `CORE_LOGIC_FINGERPRINT` through the library. Analyzer
exports its package-local hash. At analyzer policy construction, combine those two
constants with domain `omasafe.detector-logic.v1` and length-prefixed values to
produce `detector_logic_fingerprint`. Analyzer's build script never reaches into
`../omasafe-core/src/bounds.rs`. Bounds values still participate separately in
`LimitsConfiguration`; changes to their implementation also change core's hash.

Hash exact source bytes, not an AST. Do not use Git state, timestamps, absolute
checkout paths, plugin bytes, or network resources. Missing required package-local
inputs fail the build; there is no constant/empty fallback. Include no declaration
JSON in this Rust-source hash, avoiding the self-reference described below.

Add optional, default-deserializable `detector_logic_fingerprint` to report
`PolicyIdentity`. New producers supply a 64-character lowercase hex digest; legacy
missing/null is not a current full identity. Keep analyzer version, catalog/version/
prose fingerprint, severity version, parser metadata, limits, surface, and map
identity in the full policy. Cache consumers compare the complete identity, never
its semantic projection. Test same-version detector edits, addition/removal,
relocation stability, and package-local builds.

### Review identity: declared per-rule meaning, not a filtered build version

Introduce `RuleSemanticIdentity` and a `rule_semantic_identity_digest(rule_id)`
projection. Its canonical payload contains: schema `omasafe.rule-semantics.v1`,
rule ID, `review_revision`, actual severity, supported result roles, relevant
analysis methods/parser feature and grammar versions, relevant semantic-limit
values, normalization semantics revision, and supported runtime-surface revision.
Publish an explicit per-rule dependency mapping for parser/limit inputs; missing
mappings fail validation rather than silently dropping dependencies. A shared
predicate change increments all affected rule revisions.

Exclude package version, raw source hashes, catalog release number, prose/title/
guidance fingerprint, presentation budget, and timestamp. Merely omitting the byte
hash while retaining package version and prose-sensitive catalog content would
leave the review-churn problem largely intact. New v0.2.4 rows start at revision 1;
legacy decisions have no such identity and require one-time reconfirmation.
Subsequent predicate, evidence-method/confidence, or acceptance-meaning changes
increment the affected `review_revision`; cosmetic edits do not.

A manually maintained revision alone is insufficient: an unreviewed detector edit
must not inherit suppressions just because someone forgot a bump. Add package-owned
`crates/omasafe-analyzer/review-compatibility.json` with reviewed declarations keyed
by the full detector hash and the semantic-catalog digest for the actual feature
configuration. A declaration records baseline declaration ID, affected rule IDs,
classification (`semantic-change` or `review-compatible`), reviewer, date, and
rationale, plus sorted `rule_semantic_digests` and `rule_review_revisions` maps.
Its ID is the canonical declaration digest. The semantic-catalog digest hashes
the canonical rule-ID → semantic-digest map; it excludes the declaration file.
These retained maps let readers verify an old declaration covers an old record,
without reconstructing old semantics from today's code. Preserve declaration
history; unknown/retired declarations cannot authorize cross-build reuse.
Support all four parser-feature projections explicitly. Bootstrap v0.2.4 entries
have a null baseline; subsequent entries require a valid acyclic baseline link.

The full `PolicyIdentity` also carries optional `rule_semantics_catalog_digest`
and `review_compatibility_declaration_id`. An undeclared build emits null for the
latter. Because declaration JSON is outside the Rust-source hash, recording a
review does not recursively change the hash it declares. Declaration content is
packaged via `include_str!` and tracked for rebuilds. The full policy changes when
its declaration status changes, so cached compatibility status cannot be stale.

Add `scripts/check-analysis-semantics.py` to validate current declarations, baseline
links, feature projections, and affected-rule revision changes in the release gate.
A review-compatible declaration requires unchanged semantic rows and recorded
regression evidence; a semantic change names and revises affected rows. This is
maintainer-reviewed compatibility evidence, not automated proof of semantic
equivalence or protection against a malicious same-user editor. Unlisted builds
still scan and cache, but cannot reuse cross-build reviews. Tests must verify that
forgetting both a revision bump and declaration fails compatibility reuse and the
release gate. Exact same-build explicit review remains usable.

### Distinguish readable snapshots from valid analysis

`producer_compatible` in `omasafe-core/src/scan_snapshot.rs` accepts 0.2.x
producers for format compatibility; it does not establish freshness. Retain that
separation and the hard validation of exactly six components:
`inventory`, `trust`, `marketplace`, `analysis_policy`, `enforcement`, `runtime`.

For `installed-analysis`, `scan_context_fingerprints` hashes the complete new
`PolicyIdentity` inside `analysis_policy`. For `installed-basic`, retain
`not_applicable`. Do not add a seventh component or bump the context schema.
A v0.2.3 analysis snapshot remains readable as cached history; validation under
v0.2.4 returns stale with `analysis-policy-changed`. An unvalidated read remains
explicitly cached/unvalidated and must not become fresh by virtue of its version.

Detailed `analysis-snapshots` entries already compare the serialized policy
exactly. Old/missing/different detector identity is a cache miss; perform the
existing fresh-analysis path. Do not rewrite the old entry until a complete
replacement is ready. Failed/aborted analysis never commits a partial cache.

C3/C4 change cached presentation too. Bump the private detailed-analysis cache
schema from `omasafe.analysis-cache.v1` to `.v2` so old unsanitized/old-format
results cannot hydrate as the new report. This is a cache schema change, not an
analysis envelope change. Activate the v2 writer only when C4's complete transform
is integrated; interim new-format reports bypass detailed cache reads/writes.
Store presentation/redaction before persistence; require the v2 presentation
version and redaction marker and validate its shape before replay. Future presentation-only revisions
can invalidate this cache without altering source or findings fingerprints.

### Migrate suppression and triage compatibility without weakening cache checks

The current suppression implementation compares the complete serialized policy;
C0 must change that mechanism deliberately. Retain `SuppressionRecord.policy_identity`
as immutable full producer provenance. Add optional `rule_semantic_identity_digest`
and `review_compatibility_declaration_id` fields to new records; schema-v1 records
without them remain readable historical data. Do not fabricate new identities
from the current rule implementation or overwrite an old acceptance.

First require an active record and the existing rule/plugin/path scope match in
every branch. Then honor an explicit acceptance with the exact same full producer
identity; otherwise require matching rule semantic identity and valid stored/current
compatibility declarations covering that identity. An undeclared current build,
unknown declaration, or semantic
mismatch cannot reuse a cross-build suppression. Surface reconfirmation rather
than applying it. Audit every suppression call site so the old full-policy-only
path cannot bypass or accidentally override the new comparison.

Legacy v0.2.3 records need one-time reconfirmation because their original semantic
projection is unknown. Thereafter, a declared cosmetic edit misses the cache but
retains compatible review decisions. A changed predicate or evidence attribution
reconfirms affected rules; unrelated rules retain compatible reviews. Downgrading
to an older CLI remains conservative because it only knows full-policy matching.

Ledger v2 uses the same per-rule compatibility boundary, with full producer and
declaration IDs retained as provenance. Current precision counts use only current
emitted occurrences with a valid compatible label; historical records are not
added to the current denominator. New/missing/changed occurrences remain visible
as untriaged or detection deltas. This permits accumulation of useful labels
without claiming every historical detector had identical precision.

Trust baselines remain source history. Changes to full analyzer identity stay
analyzer-update events, never source drift. Keep enforcement decisions and exact
expiring overrides bound to full source/analysis/enforcement identities; semantic
review reuse must not broaden a lifecycle override. Preserve the existing
findings-only fingerprint (including its legacy confidence component). Occurrence
identity is separate, as specified in the report contract.

## Python Detection Contract

### Frontend and feature layout

Add exact dependency `tree-sitter-python = "=0.25.0"`, optional, alongside the
existing `tree-sitter = "=0.26.13"`. Introduce `python-parser` in analyzer and CLI;
the CLI defaults become `["qml-parser", "python-parser"]`. Analyzer defaults
remain empty. Commit the resolved lockfile and include the grammar in provenance.

The upstream pinned [manifest](https://raw.githubusercontent.com/tree-sitter/tree-sitter-python/v0.25.0/Cargo.toml)
and [Rust binding](https://raw.githubusercontent.com/tree-sitter/tree-sitter-python/v0.25.0/bindings/rust/lib.rs)
provide the language-function interface. They do not prove compatibility with
this workspace's runtime: C0 must compile and load this exact pair before C2.
If the smoke check fails, resolve and record a tested pin at G0; do not quietly
switch parsers during detector implementation.

Record `parser_versions["python"]` as `tree-sitter-python/0.25.0` or
`lexical-fallback-no-python-flow`. Keep the existing `analysis.parser` QML
metadata meaning; add Python metadata through `parsers` in the report contract.

Change dispatch deliberately: parse each Python file once and run the new flow
pass once, rather than attempting flow inside `analyze_script_unit`'s physical-line
loop. Retain the legacy line loop only for unaffected lexical families, with the
old `python_fetch_to_exec` block removed in all feature configurations. A disabled,
failed, or degraded Python parser must not fall back to same-line co-occurrence
for the existing download-execute finding.

**Explicit fallback detection regression:** with `python-parser` disabled,
v0.2.4 no longer emits `oma.python.download-execute` for the inline
`exec(requests.get(...).text)` form detected by v0.2.3. Removing the unsound
co-occurrence fallback trades that detection for the named `python-parser-disabled`
coverage gap, retained relevant capabilities, and partial Python coverage. The
shipped default CLI includes the parser. Put this exact change in release notes
and packager guidance; it is a named P09 acceptance case, not silent loss.

### Supported local model

Implement separate syntax lowering and evaluation modules. Lower statement lists
with locations into `Import`, `Assign`, `Call`, `Scope`, `Branch`, and `Barrier`.
An expression has `Static`, `NetworkResponse`, `NetworkBytes`, or `Unknown`
provenance plus bounded observation references. This models static possibilities;
it never imports modules, evaluates target expressions, or executes Python.

| Construct | Required semantics |
| --- | --- |
| Imports | Recognize `import requests [as r]`, `import urllib.request [as u]`, `from urllib.request import urlopen [as f]`, and `import os/subprocess [as alias]`. Resolve exact qualified names through an import environment. |
| Producers | `requests.get(URL).text/.content`, `urllib.request.urlopen(URL).read()`, and the corresponding explicitly imported aliases. A response object alone is not downloaded code bytes. |
| Assignment | Simple name assignment, parenthesized expressions, and name-to-name aliases preserve provenance. Overwrite/delete kills old provenance. Chained, destructuring, attribute, or subscript assignments are barriers unless explicitly lowered correctly. |
| Sinks | Builtin `exec`/`eval` first argument; `os.system` command string; `subprocess.run/Popen/call/check_call/check_output` with a modeled `shell=True` command string or literal interpreter argv whose `-c` operand carries network bytes. |
| Non-sinks | Downloaded text passed as an ordinary argument to a fixed executable, a URL passed to a downloader, response status handling, printing, or writing a file without a modeled execution edge. |
| Shadowing | Function-local assigned names are local throughout that function, including before assignment. Rebinding imports/builtins kills that resolution. Star imports and dynamic namespace mutation invalidate relevant resolution and disclose a gap. |
| Scopes | Analyze module and each function body independently; do not infer function invocation. Inherit only unshadowed import bindings, never mutable outer data provenance. Parameters start unknown; decorators/default expressions are separate outer expressions. |
| Branches | Analyze feasible local arms independently. Join only identical provenance at a shared successor; disagreeing arms become unknown with an explicit gap if consumed by an execution sink. No inference that one arm definitely ran. |
| Barriers | Loops, try/exception/finally, closures, comprehensions, generators, reflective calls, dynamic attribute access, and unknown transformations do not transmit a proved chain. Conservatively invalidate affected values/imports; unknown side effects can invalidate the local environment. |

Emit `oma.python.download-execute` only with a supported network-bytes → code
argument connection. Record source and sink locations even on separate lines;
include assignments if room permits. Expressions split over parentheses and
semicolons must behave like their equivalent multiline forms. Unknown relevant
execution arguments get typed unresolved-flow coverage, not a fabricated finding.

Reverse-shell and privilege detectors remain lexical/partial and retain their
existing supported forms. Publish the reverse-shell multiline gap in rule support
and report coverage; do not claim Python is fully analyzed because it parsed.

### Bounds and failure handling

Proposed constants in `omasafe-core/src/bounds.rs`, included in
`LimitsConfiguration`: maximum Python flow source 1 MiB, syntax nodes 50,000,
visited statements 2,048, expression/assignment depth 16, live bindings 1,024,
and one shared per-file parsing/flow deadline of 50 ms. Bound work by the outer
analysis deadline too. Use the parser cancellation callback/deadline rather than
checking time only after parsing. Parse errors in a unit make that unit unresolved;
do not derive flows across an error subtree. Oversized files are not parsed as
arbitrary prefixes: retain inventory and lexical observations with a size gap.

Use stable reason codes `python-parser-disabled`, `python-parse-error`,
`python-flow-source-limit`, `python-flow-node-limit`, `python-flow-statement-limit`,
`python-flow-depth-limit`, `python-flow-binding-limit`, `python-flow-time-limit`,
`python-flow-unsupported`, and `python-reverse-shell-line-only`. Anchor a path and
location when available. Wall-clock exhaustion is a disclosed limit, not a
promise of identical output on machines with different loads.

## Shell Staged Execution Contract

Move staged tracking into `detect/shell/staged.rs`; consume existing `ShellProgram`
logical units and typed command modes. Do not maintain a second physical-line
parser for the same behavior. Limit traversal to 1,024 logical units and the
existing 25 ms staged deadline, shared across nested traversal. Name/update the
corresponding policy limit explicitly when replacing the physical-line bound.

Track a static path's latest content provenance and separately its known execution
permission. Download provenance records producer location, URL if statically known,
and path spelling. Preserve literal path spelling; do not resolve symlinks, expand
an unknown working directory, or equate distinct path spellings by guessing.

- Recognize supported curl/wget output operands and stdout redirected to a literal
  file using existing command models. Never infer a download from prose or a URL
  argument to an unrelated command.
- An interpreter reading that path in script-file mode consumes code without
  requiring chmod. Respect flags and `--`; `sh -c 'echo text' PATH` does not read
  PATH as its script. An interpreter syntax-check mode is not execution.
- Direct execution requires supported execution-permission evidence (for example,
  the existing chmod forms); otherwise disclose unresolved execution feasibility.
  Do not conflate that missing permission with interpreter-file execution.
- Model a fetch success path through sequence/`&&`. A `curl ... || sh PATH` failure
  arm cannot claim newly downloaded content. Known-false branches do not execute;
  uncertain guards are possible paths, not proof of success.
- A known write/truncate/delete/rename to the path kills or replaces provenance;
  an unknown writer or unsupported control/alias involving it makes it unresolved.
  Never carry a stale download through a mutation the model cannot interpret.
- Preserve existing inline pipelines, decoders, heredoc ownership, wrappers, and
  stdin execution checks. This slice fixes staged provenance; it is not a shell
  frontend rewrite.

The original `chmod` positive remains detected, and the no-chmod interpreter
case gains the same stable rule ID with a truthful evidence chain.

## Rule Meaning and H5/H6 Contract

Keep rule IDs and severity fixed. For every catalog entry produce an audited
support record: emitter(s), capability/finding/indicator roles, supported
language/method, predicate, known gaps, benign example, positive/negative fixture
references, and review guidance. A rule may cover both a capability and a
suspicious predicate; do not force that into one ambiguous result kind.

Background input/capture/persistence findings require an observed timer, startup,
or lifecycle trigger around the sink. A click handler is interactive context,
not proof of consent; a dynamic argument or neighboring network operation does
not establish background execution. Unknown trigger retains capability and
coverage, not the background ID. No new dynamic-input or capture-egress ID is
introduced in this release.

Every result emitted by the H5/H6 line-oriented passes uses lexical confidence
and `analysis_method=lexical-correlation`, including
`oma.{qml,script}.sensitive-data-egress` and context tamper findings. Do not borrow
`outcome.confidence` from another frontend. AST-originated rules keep AST attribution.

The sensitive-data-egress predicate retains its stronger scoped read/egress
connection, but review text becomes “a sensitive read is connected to an outbound
operation; inspect the data, destination, and intended use.” Do not assert
exfiltration intent, hidden behavior, or consent. Required H6 tests include:

- Positive: sensitive value assigned, then used in the supported outbound argument;
  and a supported direct read nested in an outbound operation.
- Negative: sensitive read plus unrelated request, read after the outbound call,
  benign reassignment, sibling scope, path string without a read, and comments.
- All supported languages: correct lexical attribution with parser features both
  enabled and disabled. A source location supplied by an AST does not upgrade the
  correlation predicate's method.

If these tests expose a co-occurrence false positive, constrain the existing
predicate to its documented connection rather than weakening the expectation.

## Report, Budget, and Consumer Contract

The [companion specification](../reference/v0.2.4-review-report-contract.md)
defines exact field placement, types, limits, redaction order, counts, and
selection. It is part of this plan and freezes at G2.

Implementation principles:

- Build summary counts from the complete normalized findings before selection,
  while preserving pre-/post-suppression accounting. Existing threshold evaluation
  remains before shaping. No consumer recounts a shortened array as the total.
- Full output keeps canonical finding order. Review output is a deterministic
  subset, not a prefix. Selection is family/file round-robin within severity
  bands, then the selected findings are sorted back into canonical order.
- Preserve the 1.5 MiB review ceiling and existing per-array 1,024-entry ceilings.
  Cap new evidence per finding before list selection; suppressions and coverage
  details are bounded with explicit counts too. Preserve required summary and
  all rule-family count rows before spending remaining space on evidence.
- `analysis.coverage_limitations` remains compatible; add typed coverage without
  equating omitted inventory with failed analysis. Python/shell partial coverage
  is included even when the old string limitation list is empty.
- New producers emit the new fields; legacy readers may ignore them. New consumers
  treat missing/unknown coverage, method, trigger, or policy fields as unknown.
  Array indexes are not stable finding identities.

## Slices and Execution Order

```text
C0 identity/features → C1 correctness → C2a Python + C2b shell → G1
G1 → C3a report producer/fixtures → G2 → C3b sibling consumer
C3a → C4 presentation/redaction → C5 migration/measurement/release → G4
C3b + C4 → G3
```

The graph expresses dependencies, not a request to spawn parallel agents. C1/C2
must produce evidence compatible with the G0 contract; do not postpone interface
agreement until those implementations have diverged.

### C0 — Identity, feature wiring, and contract fixtures · Size L

Changes: package-local build hashes, full/per-rule semantic identities and
compatibility declarations, suppression matching/migration, optional Python
dependency/feature, version bump, cache-v2 preparation, and identity tests.
C4 activates the v2 writer after the presentation pipeline is complete.
Add minimal typed evidence interfaces used by C1/C2 before their producers land.
C0 may define the complete G0 report types without emitting unimplemented paths.

Deliverables:

1. Same-workspace-version/different-detector hash invalidates detailed analysis.
2. Legacy installed-analysis snapshot validates stale via the existing component;
   basic snapshots remain governed by their unchanged inputs. A loaded snapshot
   without validation is never represented as freshly scanned.
3. Legacy matching, cosmetic declared reuse, changed-rule reconfirmation, and
   undeclared-build fallback obey the ordered comparison above. Raw code hash
   changes always invalidate caches; they do not alone re-key compatible reviews.
4. Python grammar load test passes with the exact locked runtime/grammar pair.
5. Default, neither-parser, QML-only, and Python-only builds compile; no-default
   build retains its no-C-parser option.
6. Each build helper has a real test target; pruned/package-local source builds
   read no sibling source file. Normal dependency packaging remains a separate gate.
7. Resolve/fetch the new grammar and commit `Cargo.lock` before offline checks.
   On the reviewed machine the Python grammar is absent from the local registry
   source cache. Use a network-enabled dependency-preparation step, then
   `cargo fetch --locked` and verified offline builds; no network fetch occurs in
   build.rs, during plugin analysis, or from target-repository tooling.

Gate: G0 baseline recorded; no detector corrections are credited to this slice.

### C1 — Rule predicates, confidence, and catalog help · Size M

Changes: H5/H6 emitters, catalog 7 → 8, support records, rule help projection.
No severity version bump and no new finding ID. Include explicit H6 High
sensitive-egress pairs; do not limit tests to Medium background rules.

Done when: interactive probes lose incorrect background findings; supported
background controls retain them; lexical findings remain lexical in AST builds;
all catalog rows resolve to real emitter/support/fixture references or explicitly
say planned/unsupported. Remove stale future-milestone and automatic-block prose.

### C2a — Python file-level fetch-to-code dataflow · Size L

Changes: new lowering/evaluator, dispatch integration, source/sink observations,
Python capability and typed gap production. Remove the old co-occurrence emitter.
Implement the supported-model table and bounds before adding more API spellings.

Done when: inline and multiline positive probes detect, unrelated subprocess
negative does not, aliases work within supported scope, reassignments/shadowing
kill stale provenance, compound/unsupported constructs disclose uncertainty,
parse/budget errors degrade explicitly, and original reverse-shell supported
one-liners retain their existing lexical results. New Python detection acceptance
applies to Python-enabled builds; fallback acceptance is a visible coverage gap.

### C2b — Shell downloaded-file interpreter execution · Size M

Changes: shell staged module over typed units, content/permission separation,
kill/barrier semantics, interpreter argument mode handling, evidence locations.

Done when: no-chmod interpreter and chmod controls both detect; unrelated file,
benign overwrite, failed-fetch `||` arm, syntax-check mode, and misleading `-c`
extra argv do not produce a new-content execution claim. Existing inline shell
families and limits remain correct in both parser configurations.

### C3a — Summary, typed evidence, coverage, and deterministic transport · Size L

Changes: typed report structs, summary/coverage builder, evidence association,
family/file selection, rule help, CLI text ordering, full/review golden fixtures.
Keep the current findings-only fingerprint and threshold decision independent
from display caps. Compute occurrence IDs before redaction and shortening.

Done when: every contract invariant has fixture coverage; full and review agree
on complete counts/fingerprint/threshold; all families remain counted under
flooding; evidence budgets hold under JSON escaping; partial-with-zero-findings
is visible; no unknown field is read as clean. Tag the producer fixture commit
at G2 before the sibling implementation begins.

### C3b — Sibling plugin/agent consumer handoff · Size M · sibling repository

Provide frozen fixtures and a compatibility note to `omasafe-plugin` and its
agent report consumer. The new view supports CLI >=0.2.4; older CLI reports use
the existing legacy view with unavailable new fields, not fabricated defaults.
New CLI behind an old plugin must keep old required fields and valid JSON.

Render counts, evidence steps, coverage/freshness, and CLI policy state. Do not
key rows by array index or assume review is a full-array prefix. Treat all
source-derived content as plain text, disable implicit rich-text/link handling,
and preserve explicit truncation and unknown states. Agent summaries cite rule,
location, evidence method, and missing coverage; they do not infer approval.

Done when: UI/agent replay fixtures cover legacy/new producers, repeat High
families, no findings with partial coverage, stale analysis, and hostile strings.
Record the sibling commit/version. The CLI can ship independently with the legacy
UI intact, but release notes may claim the new UI only after this slice passes.

### C4 — Display and AI input boundary · Size M

Changes: one presentation transform shared by text, full/review JSON, and cached
result persistence. Follow the companion contract's escaping/redaction rules.
Preserve internal identity/evidence separately from presentation. Cap and account
for source-derived lists throughout the report, including suppression details.
Also transform display copies on every `scan`, `scan-cache show` (with or without
validation), and notification output boundary. Cover both top-level alert arrays
and nested `snapshot.alerts` in JSON, limitations, and other source-derived message
fields. A v0.2.3 snapshot being stale/readable does not exempt it from redaction.
Preserve stored snapshot bytes, generation, keys, and fingerprints; never rewrite
history as a side effect of hydration. Persist-time transformation of new detailed
reports is defense in depth, not a replacement for legacy render-time handling.

Done when: hostile comments, filenames, bidi/control characters, URL credentials,
and authorization headers remain inert, attributed, bounded, and redacted in
both profiles, detailed cache replay, and legacy snapshot hydration in validated/
unvalidated JSON/text views. Distinct normalized findings remain distinct even
when their redacted strings match. Full JSON is not an opt-out from redaction.

### C5 — Occurrence triage, measurement, and release · Size M

Introduce append-only ledger v2 records with required fields:
`schema_version:2`, `plugin_id`, immutable `commit`, `rule_id`, `occurrence_id`,
`rule_semantic_identity_digest`, `observed_policy_identity_digest`,
`review_compatibility_declaration_id`, `disposition`, `note`. The compatibility key
is `{plugin_id, commit, rule_id, occurrence_id, rule_semantic_identity_digest}`;
full producer/declaration fields are retained audit evidence, not cache keys or
unconditional permission to reuse the label. Validate their declaration linkage.
Last record wins for the full compatibility key, preserving earlier rows.

A v1 `{plugin,commit,rule}` label is a historical annotation, not an occurrence
label under a declared semantic contract. Do not copy it onto every match. Report
legacy-only matches as requiring triage. A compatible v2 label can survive a
cosmetic rebuild; changed semantics/method attribution requires review even if
location and occurrence ID are unchanged. Undeclared build labels may be used
only for their exact observed full policy until compatibility is established.

Update tooling/report schemas additively where possible; if a consumer relies
on the old ledger key, provide an explicit schema dispatch rather than silently
changing its meaning. Keep historical H7/H8b reports unchanged; emit v0.2.4
reports with current counts and the still-empty blocking set. Update ledger
README, tooling self-tests, and release-gate checks that currently compare the
legacy ledger count directly to historical H8b evidence.

Publish family × language × method support, precision sample size and distinct
plugin/revision counts, untriaged/incomplete results, false negatives in labeled
fixtures, and unsupported cells. Do not equate a fixture pass rate with ecosystem
recall. No new blocking family or numeric admission threshold is introduced by
this release; admission expansion needs a separate evidence-backed proposal.

Done when: current changed-family findings in the release sample are triaged
against exact occurrences/policy; all required regression cases pass; measurement
errors/incomplete repositories remain visible; generated assets and full release
checks pass. Deleting or weakening labels to obtain a green gate is prohibited.

## Risks and Mitigations

| Risk | Mitigation / release consequence |
| --- | --- |
| Python expansion becomes a general interpreter project | Exact modeled APIs/constructs above, unknown barriers, explicit fallback, no interprocedural or reverse-shell expansion |
| New grammar/build requirements break minimal environments | Optional feature, four build configurations, tested lockfile/provenance, explicit no-parser coverage |
| Manual version discipline fails | Build-derived fingerprint plus same-version invalidation test; no seventh snapshot component |
| Identity split accidentally reuses stale reviews | Exact same-build match or declared per-rule compatibility only; legacy migration, evidence-revision tests, and undeclared-build release gate |
| Compatibility declarations become routine approvals without evidence | No automatic semantic-equivalence claim; review diff and changed-family tests, retain baseline/reviewer/rationale, and keep undeclared builds restricted to same-build acceptance |
| Added evidence hides other findings | Per-finding caps, mandatory family totals, deterministic diversity selection, bounded minimal-summary failure path |
| Schema consumers assume array prefixes or absent=false | Selection metadata, stable occurrence IDs, legacy fixtures, G2/G3 handoff |
| Redaction erases audit identity or misses secret classes | Identity before presentation; structured bounded redaction; explicit coverage limits and deliberate local raw-source inspection |
| Overly broad H6 lexical claims survive prose cleanup | Explicit High positive/negative pairs and accurate per-emitter method; fix predicate when the pair fails |
| Ledger migration empties precision evidence | Report untriaged/N/A honestly; retriage exact sample; keep blocking set empty |
| Sibling release schedule differs | CLI backward compatibility required; new UI claim waits for C3b evidence |

## Success Metrics

- Zero incorrect outcomes in the named C1/C2 positive/negative acceptance pairs.
- Every published rule has an audited support record or an explicit unsupported
  status; every changed High predicate has both positive and negative fixtures.
- Every admitted report fits the review byte bound and conserves total = emitted
  + omitted for every shortened collection/severity/family.
- Full/review shaping preserves analysis fingerprint and explicit threshold result.
- Same-version detector changes invalidate caches; declared cosmetic changes retain
  compatible reviews; changed predicates/evidence require targeted reconfirmation.
- No current-policy corpus label is inferred from a legacy rule-only record.
- No new blocking-family admission, unsupported safety score, or recall claim.
- No silent parser/coverage loss, secret-bearing known presentation patterns, or
  report-source instruction executed in the contract fixtures.

## Acceptance Criteria

C0–C5 in this repository pass their stated tests and produce the release evidence.
G0/G2 record actual reviewed commits/dates. C3b passes before claiming a new sibling
review UI; CLI release remains independently possible with documented legacy UI.
The rule/catalog version, parser metadata, cache schema, generated assets, ledger
format, README, and release notes agree. Both standard feature configurations and
focused single-feature checks pass. Existing full release and VM gates remain.

Any deferred required predicate/schema behavior must be removed explicitly from
release claims and this scope before tagging, not hidden behind a “partial” label
that contradicts its acceptance test. Partial coverage accurately represents
unsupported language behavior; it does not excuse a known incorrect supported
predicate. Historical review/probe records remain unchanged.

## Explicit Non-Goals

- New severity grading, new dynamic-input/capture-egress rule IDs, or new blocking
  family admission in v0.2.4.
- Cross-file/interprocedural flow, arbitrary Python/shell interpretation, multiline
  Python reverse-shell analysis, or proof of runtime reachability/consent.
- Arbitrary deobfuscation, native-binary semantics, runtime sandboxing, reputation
  lookups, hosted analysis, or automatic remediation/installation.
- New report actions, paging endpoints, raw-secret export flags, or AI keyword
  filters that claim to establish an instruction boundary.
- Replacing the existing findings fingerprint with capability or presentation data,
  or treating analyzer changes as source drift.
