# v0.2.1 Scan Hardening Implementation Plan

Status: draft for maintainer review, 2026-08-27 · Owner: Hung Vo · Scope source:
[`../reviews/2026-08-27-scan-rule-coverage-review.md`](../reviews/2026-08-27-scan-rule-coverage-review.md)
(revision 3)

This decomposes the nine review findings (`R-1`…`R-9`) into vertical slices `H0`–`H9`.
Each slice ends committed and verified per [`../progress.md`](../progress.md) convention and
leaves the CLI working end-to-end. The review's own priority order is the spine; where two
findings share machinery they are merged into one slice rather than split across layers, and
where one half of a finding is gated on evidence the other half does not need, the slice is
split so the ungated half is not held behind corpus triage.

## Strategy Decisions

1. **Evidence quality leads enforcement.** OmaSafe has no dataflow analysis today
   (`LexFlags` is write-only; the "chain" test is a substring check inside the sink
   expression — `detect.rs:1660`). Behavior that would need dataflow to be trustworthy ships
   first as a **capability**; a distinct evidence-backed finding ID/emitter lands only after
   H4. No rule built on capability co-occurrence ships at any point.
2. **Rule-family blocking is gated on measured precision; the enforcement mechanism is not.**
   `fixtures/corpus/expectations/dispositions.jsonl` is empty, so no rule family may join the
   hardened blocking set before H7 measures it (H8b). The enforcement *mechanism* — policy
   selection, enforcement-policy identity, override records, and blocking on
   precision-independent conditions such as coverage state, identity staleness, and failed
   postconditions — depends on none of that and ships in H8a. Reporting-fidelity fixes carry
   no false-positive risk at all and ship earliest (H1).
3. **Runtime claims are verified before they are published.** Two rules depend on unverified
   runtime behavior — remote QML reachability (R-1) and third-party reachability of
   `setPluginEnabled` (R-6). H0 verifies both on the pinned build. A rule whose reachability
   check fails ships as an indicator, never as a High finding with a fabricated anchor.
4. **Stable rule IDs and predicates.** Rule IDs and meanings are frozen at publication per
   the existing rule contract. A capability observation and a later evidence-backed finding
   use distinct IDs; “promotion” must not silently repurpose the capability ID. Severity-only
   changes bump `SEVERITY_TABLE_VERSION`; blocking eligibility belongs to enforcement-policy
   identity and can change without redefining the finding.
5. **Analysis and enforcement identities stay separate.** Analyzer `PolicyIdentity` keeps
   its existing meaning: inputs that can change analysis output. H8a adds a distinct
   enforcement-policy identity over the blocking threshold, blocking-eligible families,
   coverage requirements, installed-tree postconditions, and override schema. Decisions and
   overrides bind both identities, so neither kind of policy change can look like plugin
   drift or silently reuse an old approval.
6. **Analyzer improvement is a user-visible event, not silent.** H4 changes results on rules
   that are already published and already baselined. Per the identity contract in
   [`README.md`](README.md), that is an *analyzer improvement* event and must never share
   alert wording with source drift. H4 owns that event path and its suppression-migration
   behavior; no slice may change analysis output without a policy-identity delta and an
   event the user can distinguish from a plugin changing underneath them.
7. **No new crates.** Work lands in `omasafe-analyzer` (rules, detectors, dataflow),
   `omasafe-cli` (lifecycle, severity fidelity), and additive `omasafe-report` types for
   enforcement decisions. Dataflow and enforcement records are new modules, not new crates.

## Maintainer Review Gates

- Approve separate analyzer and enforcement-policy identities.
- Accept that first-install prevention is conditional on verified inactive staging; otherwise
  H8a protects only OmaSafe-controlled enable/re-enable and documents the native bypass.
- Approve distinct capability/indicator and evidence-backed finding IDs rather than semantic
  “promotion” of a published rule ID.
- Accept interactive-only overrides in v0.2.1 and the explicit limitation that user-owned
  audit state is not tamper-proof against a plugin already executing as that user.
- Approve H7 measured precision and ground-truth fixture detection rate as prerequisites for
  adding a family to the hardened blocking set (H8b), while allowing the enforcement
  mechanism and its precision-independent block conditions to ship in H8a.
- Approve the H4 analyzer-improvement event and suppression-migration behavior: existing
  baselines will see findings appear and disappear under an unchanged commit, and that must
  read as an analyzer change, never as plugin drift.
- Decide the hardened-mode policy for `bar`-kind plugins, which cannot be disabled without
  selecting another bar: either exempt them from automatic disable or accept a documented
  recovery path.
- Approve the H9 consumer boundary: the plugin may display and invoke CLI-owned decisions,
  but may not calculate policy, create overrides, claim complete first-install protection,
  or replace CLI/desktop notifications as the critical-alert path.
- Approve the three-field enforcement outcome model (`evaluation_state`, `outcome`,
  `authorization_basis`) over a single collapsed enum, and the rule that blocking rule IDs
  survive an override-authorized allow.
- Accept the version-skew window in which a v0.2.1 hardened CLI runs behind a v0.2 panel.
  `cliVersionMin` guards only the opposite direction. Persistence, not notification, is the
  recoverability guarantee.
- Approve the notification rule: every successful override-authorized live-state transition
  notifies at warning level, read-only evaluation never does, no age gate, and delivery is
  best-effort so a notification failure cannot roll back the operation.

## New CLI Surface (regenerate via scripts/generate-cli-assets.sh)

```text
plugins enable PLUGIN_ID [--policy advisory|hardened]     # H8a: controlled enable gate
    [--format text|json]
plugins review-update PLUGIN_ID [--expected-commit SHA] [--yes]
    [--policy advisory|hardened] [--format text|json]      # H8a: same explicit policy
plugins enforcement-status PLUGIN_ID [--format text|json] # H9: read-only last decision
plugins override create PLUGIN_ID --rule RULE_ID [--rule RULE_ID ...]
    --commit SHA --reason TEXT --expires DATE             # H8a: interactive TTY required
plugins override list [--format text|json]                # H8a
rules coverage [--format text|json]                       # H5: Baseline V3 gap summary
schedule install [--policy advisory|hardened]             # H8a: hardened includes analysis
schedule status [--format text|json]                      # H9: read-only installed policy
```

`plugins review-update` gains fail-closed postconditions in H1 and an explicit policy option
in H8a. H8a makes analysis part of the opt-in hardened schedule; the advisory schedule remains
a drift scan unless the user explicitly requests analysis. The hardened *schedule* only scans
and reports — enforcement decisions belong to `plugins enable` and `plugins review-update`, so
an unattended timer never needs an override it cannot create. H8b adds no CLI surface; it
populates the blocking-eligible family set that H8a already reads.

## Slices

### H0 — Runtime reverification and lifecycle boundary · Size M · maps to R-1, R-6, R-7

- Reverify [`../reference/omarchy-security-surface.md`](../reference/omarchy-security-surface.md)
  on the pinned Omarchy/Quickshell build and answer three specific questions the rules and
  lifecycle policy depend on:

  2. Is `setPluginEnabled` / `rescanPlugins` actually reachable from third-party plugin
     context, or only from first-party shell code?
  3. Can native install stage an exact reviewed plugin tree inactive, without placing it in

     race between filesystem placement and enabled-state mutation.
- Run reachability checks only in the clean-VM harness: serve inert QML from loopback, use a
  marker-only test plugin for IPC, and exercise install ordering in a disposable profile.
  Never test remote loading or lifecycle mutation in the maintainer's live shell/plugin tree.
- Record all three answers with the verification stamp. A negative reachability answer is a
  recorded result, not a blocker: it demotes the corresponding rule to indicator status in
  H2/H5. A negative staging answer constrains H8a instead of being papered over.
- Define the proposed `InputInjection`, `ScreenCapture`, and `SensitiveDataAccess` capability
  vocabulary and surface anchors in the reference document; add code variants with their
  H6 detectors, not as unused H0 code.
- Exit: the surface doc carries a fresh stamp answering all three questions; the catalog is
  unchanged, and the inactive-staging answer defines the honest H8a boundary.

### H1 — Fail-closed reviewed update and severity fidelity · Size M · maps to R-4, R-7 (reporting half)

The smallest change that closes an invariant violation, plus the reporting fixes that carry
no false-positive risk.

- **Fail closed on post-update state** (`main.rs:939-943`): require
  `updated_record.dirty == Some(false)`. Both `Some(true)` and `None` leave the plugin
  disabled and return an error — `None` currently is not rejected at all, although the
  pre-update check refuses the same uncertainty (`main.rs:493-503`).
- **Verify installed bytes, not staging bytes**: before re-enable (`main.rs:961-980`),
  re-ingest the installed tree and require its source identity, analysis fingerprint, policy
  identity, and coverage state to match the approved candidate. Advance trust from that
  installed-tree identity, never from the temporary checkout (`main.rs:983-989`).
- **Preserve catalog severity in alerts** (`main.rs:1580-1608`): stop emitting new analyzer
  rule IDs as a generic `warning`. Fix `track_highest_severity` (`main.rs:1710-1715`), which
  recognizes only `critical` and collapses every other nonempty value — including `error` —
  to `warning`.
- Tests: CLI-level integration tests driving `review-update` against a dirty worktree, an
  unknown-dirty-state worktree, and a worktree whose installed bytes differ from the reviewed
  candidate. Each must leave the plugin disabled with a nonzero exit.
- Exit: no `review-update` path exists from an unverified installed tree to re-enable or an
  advanced trust record; a High finding reaches the notification path as High.

### H2 — Reference sinks: remote, out-of-tree, and typed rejections · Size M · maps to R-1, R-2

One slice because both findings live in the same code path (`resolve_reference`,
`detect.rs:324`, and the `Value::Static` branch at `detect.rs:1412`).

- New rule `oma.qml.remote-component-load` (**High**, per the H0 record: `Loader.source`
  and `Qt.createComponent(...)` network loads are verified reachable on Quickshell
  0.3.1): any URL-scheme literal in those two reference positions. `apply_import_surface`
  (`detect.rs:940`) checks nothing scheme-related today.
- New indicator `oma.qml.remote-directory-import` (**not a High finding**): remote QML
  directory imports with qmldir are scanner-intercepted on the verified runtime (URL
  strings normalize to relative filesystem paths and are dropped), so the reachable High
  rule must not claim them. The indicator records the intent; guidance states that no
  remote directory import executed on the pinned build and that future runtimes must be
  re-probed before escalation.
- New rule `oma.qml.out-of-tree-reference` (**Medium**): absolute-path and traversal
  references. Rule summary and guidance must describe these as *unreviewed out-of-tree loads
  that bypass commit-bound review* — not sandbox escapes. There is no runtime sandbox.
- Add `Qt.createComponent(` and `Qt.include(` to both dynamic-code needle sets: the AST call
  list (`handle_call_expression`, currently `eval | createQmlObject | atob`) and the lexical
  set (`detect.rs:684`).
- **Typed sink-position rejections only.** Introduce a sink-position marker on reference
  candidates so `resolve_reference` can distinguish a real load sink — `Loader.source`,
  `Qt.createComponent`, `Qt.include`, `Process.command`, `execDetached`, `FileView.path` —
  from the general string sweep. `collect_ast_references` (`detect.rs:1857`) keeps every
  path-shaped string in the tree, so only sink-position rejections are reported, with a typed
  reason: `remote`, `absolute`, `traversal`, `missing-local-target`, `unsupported-scheme`.
  Non-sink strings stay inventory context.
- Fixtures: literal-remote `Loader`, remote `Qt.createComponent` (Loading→Ready), remote
  directory import with and without `qmldir` (indicator only, never the High rule),
  absolute-path load, traversal load, plus negative fixtures for icon names, format strings,
  and URLs in comments that must produce no limitation.
- Catalog impact: `RULE_CATALOG_VERSION` 3 → 4.
- Exit: the literal-remote `Loader` and `createComponent` fixtures each produce the High
  finding; the directory-import fixtures produce only the indicator; the negative fixtures
  produce zero new limitations; a non-sink unresolvable path-shaped string still produces none.

### H3 — Script pattern expansion · Size M · maps to R-3 (pattern half)

Everything in R-3 that needs no dataflow. `analyze_script_source` (`detect.rs:1177`) today
requires curl/wget and a `|`-to-interpreter on the same line.

- New rule `oma.script.reverse-shell` (**High**) and its Python counterpart: `/dev/tcp/…`,
  `nc -e`, `socat exec:`, `bash -i >&`. Highest-signal and lowest-false-positive family
  available; ships first inside the slice so H7 can start measuring it immediately.
- Extend the existing download-execute family with same-line variants that have no pipe:
  `eval "$(curl …)"`, `source <(curl …)`, `bash <(wget …)`.
- New rule `oma.script.decode-execute` (**High**): `base64 -d`, `openssl enc -d`, `xxd -r`
  feeding an interpreter. Note the shell blind spot in guidance — an unquoted base64 blob is
  not a quoted literal, so `line_literals` never sees it and the existing obfuscation
  indicator cannot fire on shell.
- New indicator `oma.script.privileged-shared-temp` for `sudo` / `pkexec` of a `/tmp` or
  `/dev/shm` path, plus a separately defined High rule
  `oma.script.privileged-shared-temp-controlled`. H3 can emit the High rule only for an
  explicit unsafe creation/ownership/mode sequence; H4 adds the connected untrusted-write
  predicate. A pathname alone does not prove attacker control, and the indicator ID is never
  repurposed as a finding.
- **Egress attribution**: record `NetworkAccess` for fetch tools (`curl`, `wget`) in scripts
  and in QML `Process` argv. Today scripts get capabilities only for sudo/systemctl/package
  managers and QML argv gets `ProcessExecution` only, so `curl https://x -d "$data"` produces
  no network capability at all. This is a precondition for every source-to-egress rule in H6.
- Fixtures: one per evasion above, each paired with a benign near-miss (a logged string
  containing `curl … | sh`, a `nc` invocation without `-e`, a `sudo` of a non-temp path).
- Catalog impact: `RULE_CATALOG_VERSION` 4 → 5.
- **Hand off to the H7 early pass.** The two families expected to qualify for hardened
  blocking both exist at the end of this slice. Start their corpus triage here and run it
  concurrently with H4–H6 rather than after them; see H7. Nothing in H4–H6 changes what these
  two rules match, so their measurement does not need to wait.
- Exit: every evasion fixture produces its rule; every near-miss fixture produces none;
  shell/Python coverage remains labelled `Partial` regardless of outcome; triage of
  `oma.script.reverse-shell` and `oma.script.privileged-shared-temp-controlled` is underway.

### H4 — Bounded intra-file dataflow · Size L · maps to R-3 (dataflow half), unblocks R-5, R-8

The single largest capability gain, and the prerequisite for every escalation rule.

- New `dataflow.rs`: bounded intra-file analysis over the QML/JS AST — local assignment
  tracking, then callback-parameter awareness. Explicit bounds (statement count, assignment
  depth, per-file time) that participate in policy identity; exceeding a bound degrades
  coverage visibly rather than returning a clean result.
- Retire the substring provenance heuristic in `classify_value` (`detect.rs:1660`), which
  matches `responseText` / `.response` / `.text(` inside the sink expression itself. Its
  known evasion is one variable assignment:
  `var d = xhr.responseText; Quickshell.execDetached(d)` currently classifies as a plain
  `dynamic-command` and stays capability-only. Replace with real assignment tracking.
- Delete or consume `LexFlags` (`detect.rs:559,588,1476,1486,1778,1788`) — currently written
  in six places and read in none.
- Staged script chains: a separate bounded lexical state tracker pairs fetch → `chmod +x`
  → execute of the fetched path at `LexicalFallback` confidence. Do not imply that the
  QML/JS AST dataflow engine parses shell.
- Computed-reference resolution for the H2 sinks: a `Loader.source` assigned from a literal
  earlier in the file resolves; one assigned from network or user input escalates.
- **Analyzer-improvement event and baseline migration.** This slice changes results on rules
  that are already published and already baselined: dataflow adds detections the substring
  test missed, and retiring that heuristic removes findings it produced spuriously. Users will
  see findings appear and disappear under an unchanged commit. Per the identity contract in
  [`README.md`](README.md) this is an *analyzer improvement*, a different event type from
  source drift, and must not reuse drift wording. Required behavior:
  - The analyzer `PolicyIdentity` delta is the signal; the resulting alert names the analyzer
    change and offers re-review, never "the plugin changed."
  - Existing trust baselines stay valid — an analyzer change is not source drift and must not
    invalidate a pinned identity or demand a re-trust.
  - Decide and test suppression behavior explicitly. A suppression scoped to a rule ID whose
    evidence predicate changed must neither silently keep suppressing new evidence nor
    silently lapse. Carry the analyzer identity on the suppression record so a predicate
    change surfaces the suppression for re-confirmation instead of resolving it either way.
- ADR recording the bounds, why intra-file (not cross-file) is the v0.2.1 scope, what
  coverage state an exceeded bound produces, and the analyzer-improvement event contract.
- Fixtures: variable-indirection versions of every H2/H3 fixture, plus bound-exhaustion cases
  that must degrade coverage rather than report clean, plus a baselined-plugin fixture whose
  results change across the H4 boundary.
- Exit: the one-assignment evasion of the existing chain rule is detected; every bound
  exhaustion is visible in coverage state; fingerprints stay deterministic across runs; a
  plugin whose findings change under an unchanged commit produces an analyzer-improvement
  event with its own wording, keeps its trust baseline, and surfaces any affected suppression
  for re-confirmation.

### H5 — Payload reachability tiers, anti-OmaSafe detection, equivalence gaps · Size L · maps to R-6, R-8

- **Bundled binary tiers** (`oma.payload.bundled-binary`), replacing the current situation
  where `PayloadKind::ElfBinary` and friends sit in the inventory as `Unsupported` coverage
  and never reach the alert path:
  - unreferenced → capability / inventory warning
  - referenced or executed from QML or a script → **Medium**
  - remote-downloaded, or digest changed outside an approved update → **High**

  Reachability comes from the existing invocation-edge machinery plus H4. H8a may block a
  referenced executable until its exact digest is approved, but must not rewrite the Medium
  analyzer severity based on enforcement state. Generic “unsigned” is not a usable analyzer
  predicate without a signing scheme.
- **Anti-OmaSafe detection**, framed in catalog guidance as *detection of intent, not
  protection*: `oma.context.omasafe-state-tamper` (**Medium**) for writes into
  `~/.local/state/omasafe`, into sibling plugin directories under `~/.config/omarchy/plugins/`,
  or `git` invoked against another plugin's checkout. Report copy must state plainly that a
  quiet result does not mean OmaSafe is protected — once a plugin runs with the same user
  authority, equivalent mechanisms are unbounded. Real self-protection needs a boundary
  (sandboxing, separate service authority, protected state, pre-execution gate) and belongs
  with the v0.5 privileged-helper work.
- **IPC lifecycle mutation**: emit `oma.shell.ipc-injected-objects` and its
  `ShellIpcInventory` capability — the rule is published (`rules.rs:313-321`) but no detector
  emits it. Ship as a **capability** regardless of H0's answer; add a distinct finding rule
  only if H0 confirms a concrete third-party lifecycle-mutation sink. Severity is not
  automatically High: disabling the bar widget does not disable the independent CLI and
  desktop-notification path that critical alerts already use.
- **Equivalence honesty**: change the `bundled-executable-binary` relation from
  `structural-equivalent` to the existing `partial-overlap` vocabulary until tier two lands;
  keep “inventory-only” in its note. Its current note already admits the result is a payload-
  inventory fact (`equivalence/baseline-v3.json:87-90`). Add `rules coverage`, surfacing the
  current `not-covered` set and relation for every Baseline V3 entry. H3 may move
  `privileged-process-control-from-shared-temp` to `partial-overlap`; it must not disappear
  from the summary merely because the evidence-backed subset is implemented.
- Catalog impact: `RULE_CATALOG_VERSION` 5 → 6 and `EQUIVALENCE_MAP_VERSION` revision bump.
  `SEVERITY_TABLE_VERSION` stays at 1 unless an existing rule's severity actually changes;
  adding new tiered rules is catalog change, not a severity-table rewrite.
- Exit: `rules coverage` prints the gap set; a referenced ELF produces a Medium result; an
  unreferenced one produces a capability; the IPC rule has an emitter and a verified anchor.

### H6 — User-data capability family · Size M · maps to R-5

Every item ships as a **capability or indicator**. Escalation predicates use H4 dataflow and
require a sensitive source connected to egress, hidden or background collection, dynamic
attacker-controlled input, or concrete suspicious persistence behavior. Capability
co-occurrence is never an escalation trigger. Each evidence-backed escalation gets its own
stable finding ID rather than repurposing the capability/indicator ID.

- `oma.qml.sensitive-path` and its script counterpart (**capability**): `~/.ssh`, `~/.gnupg`,
  keyrings, browser profiles, `~/.aws`, `~/.config/gh`, `~/.kube`, wallet directories. The
  filesystem rule's guidance already promises this (`rules.rs:180`) and nothing implements it.
  `/etc/shadow` stays out of the High set — normally unreadable to the user, so its presence
  is an intent indicator at most.
- Input injection (**capability, escalating**): `ydotool`, `wtype`, `wlrctl`,
  `hyprctl dispatch sendshortcut`. These back legitimate accessibility and automation
  workflows; escalate on background or timer-driven invocation, or dynamic keystroke content.
- Screen capture (**capability, escalating**): `grim`, `slurp`, `wf-recorder`, `hyprshot`.
  Legitimate for screenshot plugins; escalate on timer/service-driven capture with no
  user-visible trigger, or capture combined with a dataflow-confirmed egress edge.
- Clipboard tools: add `wl-paste`, `cliphist`, `xclip` — current detection is the literal
  token `clipboard` (`detect.rs:662`), so `wl-paste --watch <cmd>`, a persistent clipboard
  monitor, is missed entirely. Encode direction: `wl-copy` *writes* the clipboard and is not
  theft; read-and-watch forms carry the risk.
- Persistence expansion (**capability, escalating**): XDG autostart, `~/.config/systemd/user`
  unit files written via `cp`/`tee` (the `systemctl` token alone misses unit-file drops),
  shell rc files, `~/.config/environment.d`, `crontab`/`at`, and Hyprland `exec-once` lines in
  `~/.config/hypr/*`. Installing a user service can be entirely expected. Omarchy's current
  manifest has no permission/capability declaration, so absence of a declared need is not
  evidence. Escalate only on concrete signals such as hidden/background activation, dynamic
  or untrusted content, a security-sensitive startup target, or a target clearly unrelated
  to the declared plugin kind.
- Catalog impact: `RULE_CATALOG_VERSION` 6 → 7.
- Exit: a screenshot plugin and a clipboard-manager plugin from the corpus produce
  capabilities and zero findings; a fixture with a dataflow-confirmed sensitive-read-to-egress
  edge produces a finding.

### H7 — Corpus dispositions and precision measurement · Size L · maps to R-9 · gates H8b

Runs in two passes. The **early pass** starts as soon as H3 lands and triages only
`oma.script.reverse-shell` and `oma.script.privileged-shared-temp-controlled` — the two
families expected to qualify for blocking first. Nothing in H4–H6 changes what those rules
match, so the early pass runs concurrently with those slices instead of behind them, and H8b
is not held behind triage of families it will never block on. The **full pass** covers the
remaining families once H5 and H6 have added them.

- Populate `fixtures/corpus/expectations/dispositions.jsonl` — currently zero triaged records —
  with true-positive and false-positive dispositions for every High rule family, against real
  pinned community plugins.
- Measure and publish per-family precision from fully triaged emitted results. Measure
  detection rate against independently labeled adversarial/mutation fixtures; do not call
  the corpus ledger “recall,” because missed findings never enter it. Known false-positive
  shapes to characterize explicitly: raw `Polkit` / `PamContext` tokens in quoted prose
  becoming High findings, and `atob()` treated as dynamic code execution when decoded bytes
  are never evaluated.
- Add adversarial negative and boundary fixtures for every evasion introduced in H2, H3, and
  H4.
- Release gate: zero untriaged and zero known-false-positive corpus results, plus 100%
  detection of the declared ground-truth adversarial patterns, in any family marked
  blocking-eligible. This is not a claim of 100% ecosystem recall.
- Exit: a published precision table and ground-truth fixture detection table per rule family;
  the blocking-eligible set is named by measurement, not intuition. Expected first entries
  are `oma.script.reverse-shell` and `oma.script.privileged-shared-temp-controlled` — expected,
  not assumed: if neither clears its threshold, the set is legitimately empty and H8a still
  ships (see H8b).

### H8a — Enforcement mechanism · Size M · maps to R-7 (enforcement half) · not gated on H7

Opt-in mode. The advisory default reporting contract is unchanged. This slice ships the gate,
the identities, and the override record. It blocks only on **precision-independent**
conditions, so it does not depend on corpus measurement and can land alongside the H7 early
pass.

- `plugins enable PLUGIN_ID --policy hardened`: for a plugin tree already installed and
  inactive, scan the exact installed bytes before enable/re-enable. If H0 verifies a native
  inactive-staging primitive, extend this flow to first install; otherwise do not claim that
  it protects native first install.
- Apply the same explicit `--policy advisory|hardened` selection to `plugins review-update`.
  The default stays advisory for compatibility; under hardened policy, no update path may
  re-enable or advance trust without satisfying this slice's block/override decision.
- Block re-enable on the **precision-independent** conditions: executable unsupported payloads
  without exact-digest approval, skipped or truncated analysis, stale surface, analyzer
  identity, or enforcement-policy identity, and failed installed-tree postconditions. None of
  these depend on rule precision, so all of them are enforceable the day this slice lands.
  Read the blocking-eligible rule-family set from enforcement-policy configuration — H8b
  populates it; an empty set here is valid and is what ships if H7 qualifies no family.
  `review-update` additionally requires the expected diff against its trusted baseline. A
  first review has no prior baseline by definition, so it presents the full tree and must not
  fail merely because a historical diff is unavailable. Present coverage-state counts, which
  `review-update` currently omits — it prints aggregate limitation strings (`main.rs:765-770`)
  but no per-state counts.
- **`bar`-kind carve-out.** A whole-bar plugin cannot be disabled without selecting another
  bar (`omarchy-security-surface.md`, plugin-kind prioritization), so a blocked hardened
  update on one degrades the desktop rather than a widget. Hardened mode must not leave a
  `bar`-kind plugin disabled as a side effect of a blocked update: block the *update* and
  leave the previously trusted revision live and enabled, then alert. Where that is not
  possible — the update already mutated the tree and the prior revision cannot be restored —
  print the recovery sequence before exiting, and note that the CLI and desktop-notification
  paths remain available with no bar, by design.
- `plugins override create`: scoped, audited, expiring override bound to plugin ID, exact
  commit, tree/content digest, analyzer identity, enforcement-policy identity, rule IDs,
  coverage limitations, reason, and expiry. Require an interactive TTY and typed confirmation;
  do not offer `--yes` or wildcard plugin/commit/digest/rule scopes. Store with private modes,
  locking, and atomic replacement. `review-update --yes --expected-commit` binds *what* is
  selected for its existing unattended workflow; it does not create a hardened override.
  Describe the override record as auditable, not tamper-proof against already-running code
  with the same user authority.
- Add a separate enforcement-policy identity covering blocking threshold, blocking-eligible
  families, coverage requirements, installed-tree postconditions, and override schema.
  Preserve analyzer `PolicyIdentity`; bind decisions and overrides to both identities.
- **Persist every enforcement decision** in the three-field form H9 freezes —
  `evaluation_state`, `outcome`, `authorization_basis` — retaining blocking rule IDs even when
  an override authorized an allow. Persistence is what makes a decision recoverable after a
  missed or suppressed notification, and it is what `plugins enforcement-status` reads. Every
  record carries a stable `audit_event_id`.
- **Audit every attempted override use, including failed operations.** The audit record is
  written on attempt, not on success, so a mutation that fails midway still leaves evidence
  that an override was exercised.
- **Notification rule — transitions, not evaluations.** Every successful live-state transition
  authorized by an override emits a warning-level, CLI-owned desktop notification. Read-only
  evaluation does not notify. Override age affects displayed context, not whether the
  notification occurs.
  - Notify: successful overridden enable, re-enable, and reviewed update.
  - Do not notify: scans, status reads, override listing, or merely evaluating policy.
  - A failed mutation emits a separate failure/recovery notification, not the transition one.
  - No age gate. A fresh unexpected use matters as much as a stale one — arguably more, since
    the same-user boundary in R-6 means an already-running plugin can create and immediately
    exercise its own override.
  - Payload carries plugin ID, operation, rule IDs (or count), override age, expiry, and the
    `audit_event_id`. No raw reason or evidence text — stricter than the panel's bounded
    evidence rule, because a notification has no redaction surface.
  - Delivery is best-effort: a notification failure must never roll back the operation. The
    CLI warns on stderr and retains the persisted audit event, which remains the source of
    truth.

  Volume stays low by construction — an exact-identity override is only "used" when it changes
  an otherwise-blocked lifecycle outcome.
- Blocks and failed recovery notify as well, per the same CLI-owned path.
- `schedule install --policy hardened` generates the daily unit with
  `scan --include-analysis --notify --only-new`. Advisory scheduling stays unchanged.
- **Boundary:** direct native install/enable/update commands bypass OmaSafe policy. Keep
  after-the-fact detection, document the bypass, and retain the upstream pre-activation-hook
  proposal. If H0 finds no inactive staging primitive, this remains an explicit residual
  risk rather than a failed H8a promise.
- **Same-user authority boundary:** a previously enabled malicious plugin can invoke the CLI
  or modify user-owned state, including overrides. H8a is a pre-execution risk-reduction gate,
  not recovery from an already-compromised user session. Tamper-resistant decisions require
  the separate-authority design deferred with R-6/v0.5.
- ADR recording the enforcement staging ladder and what evidence promotes a family from
  audit-only to blocking.
- Exit — stated against precision-independent conditions so the slice is completable whatever
  H7 measures: hardened mode blocks enable of an already-inactive tree carrying a truncated
  analysis and of one carrying an unapproved executable payload; advisory mode reports both
  and enables; an expired override fails closed; an analyzer change and an enforcement-policy
  change produce their respective identity deltas, never a drift alert; a blocked hardened
  update on a `bar`-kind plugin leaves the prior trusted revision live. First-install
  prevention is an exit criterion only if H0 verifies inactive staging.

### H8b — Blocking-eligible rule families · Size S · maps to R-7, R-9 · requires H7

Populates what H8a already reads. No new CLI surface and no new mechanism.

- Add each family that cleared its H7 threshold to the enforcement-policy blocking set, with
  its measured precision and ground-truth detection rate recorded alongside it.
- Every addition is an enforcement-policy identity change, never an analyzer change: the rule
  itself is untouched, only its blocking eligibility moves.
- **An empty set is a valid outcome.** If no family clears its threshold, H8a ships as the
  hardened mode for this release and blocking stays limited to the precision-independent
  conditions. That is the honest result, not a failure — it is exactly the staging ladder in
  R-9 working as designed.
- Exit: for each admitted family, hardened mode blocks its fixture before enable and advisory
  mode does not; the published precision figure that admitted it is recorded in the
  enforcement policy; adding or removing a family produces an enforcement-policy identity
  delta and no drift alert.

### H9 — Plugin visibility and safe controls · Size L · maps to R-7, R-8, R-9 · after CLI contracts freeze

Implemented in the sibling `omasafe-plugin` repository after H1–H8b have frozen their JSON
contracts. The existing plugin already has the v0.2 four-tab panel, analysis findings,
capabilities, coverage limitations, rule explanations, reviewed update, and bounded process
collectors. H9 extends those views; it does not introduce a new navigation architecture.

**CLI handoff contract**

- The CLI remains the sole owner of findings, severity, coverage classification, policy
  evaluation, blocking eligibility, and override validity. QML renders versioned decisions;
  it never recreates enforcement logic from individual fields.
- Add an optional `result.enforcement` object carrying its own
  `"schema": "omasafe.enforcement.v1"`, **nested inside the existing `omasafe.report.v1`
  envelope** exactly as the v0.2 `analysis` object was — not a new top-level document. The
  panel already reaches for `report.result.analysis` (`Panel.qml:3180`), the report contract
  commits to additive optional fields with no breaking envelope bump inside v0.x, and one
  envelope keeps `plugins analyze` and `plugins enable` parseable by the same code path. Emit
  it from hardened `plugins enable` and `plugins review-update`, and expose the last persisted
  decision through read-only `plugins enforcement-status`.
- **Model the outcome as three orthogonal fields, not one enum.** `override` is not an
  outcome; it is why an outcome was permitted. Collapsing them makes "allowed because policy
  passed" indistinguishable from "allowed despite blockers," which is the single most
  important distinction a consumer has to draw.
  - `evaluation_state`: `evaluated` | `not-evaluated`
  - `outcome`: `allow` | `block`
  - `authorization_basis`: `policy` | `override` | `null`

  `blocking_rule_ids` and the coverage/identity reason codes stay populated when
  `outcome = allow` and `authorization_basis = override` — that combination is precisely the
  allowed-despite-blockers case, and dropping the blockers there would erase the audit trail.
  Alongside these: stable reason codes, plugin ID, exact commit/tree/content digest, analyzer
  and enforcement-policy identities, coverage counts, override binding with `created_at` and
  `expires_at` (age is derived, never stored precomputed), `audit_event_id`, timestamp, and
  residual-boundary flags such as `native-install-not-interposed`.
- **No second per-plugin sweep — decided shape.** The panel already runs an N-invocation
  per-plugin status queue on open (`listStatusProcess`), and its own v0.2 plan calls out not
  duplicating it. Therefore:
  - Fold a **small last-decision summary** into the existing inventory result, sized for the
    Overview block — outcome, authorization basis, evaluation state, and decision timestamp.
  - Keep `plugins enforcement-status PLUGIN_ID` as the **lazy, selection-time** call for full
    detail: reason codes, blocking rule IDs, identities, coverage counts, override binding.

  This avoids both failure modes: an all-plugins payload that duplicates inventory, and a
  second N-command sweep on panel open.
- Add read-only `schedule status` JSON with installed/not-installed, advisory/hardened policy,
  report-only behavior, unit identity, and last known execution result. The plugin must not
  scrape `systemctl` output or infer schedule policy from unit text.
- Keep the schemas additive and reject malformed identity/decision combinations in CLI tests.
  Unknown enum values render as “unsupported by this plugin version,” never as allow/clean.

**Version-skew boundary (both directions)**

- *Old CLI, new plugin* is already solved and needs no new work: `cliVersionMin` and
  `cliVersionRequireIdentity` exist in `manifest.json` and are enforced in `BarWidget.qml`.
  Raise the floor to `0.2.1` when the panel starts consuming enforcement fields.
- *New CLI, old plugin* is the unsolved direction. The **window** is guaranteed — the CLI ships
  from this repository while H9 lands in the sibling only after the contracts freeze — though a
  hardened block occurring inside it is conditional on the user having opted into hardened mode
  and a blocking condition actually firing. No plugin-side setting can fix it retroactively.
- **What is actually missing is enforcement and recovery semantics, not a clean state.** A v0.2
  panel still renders findings and still shows a warning badge, so the user is not looking at a
  false all-clear. What that panel cannot express is that an operation was *blocked*, why, and
  what the recovery step is. State the gap that precisely; overstating it as a
  quiet-means-secure failure misdescribes the risk and would justify heavier mitigation than
  the situation needs.
- **Scope notifications to state transitions, not evaluations.** Blocks, failed recovery, and
  every *successful live-state transition authorized by an override* notify at warning level.
  Read-only paths — scans, status reads, override listing, policy evaluation — never do, and an
  allowed hardened decision on a clean plugin is routine and stays silent. See H8a for the full
  payload and best-effort delivery rule.
- **Persist every decision so a missed notification stays recoverable.** Persistence, not the
  notification, is what makes this robust: `plugins enforcement-status` can answer after the
  fact regardless of whether a notification was seen, suppressed, or fired while the session
  was logged out. Notification is the prompt; the persisted record is the source of truth.
- One mitigating detail: the current panel accepts only exit codes 0 and 4 on the analyze path
  (`Panel.qml:3170-3176`) and turns anything else into a visible error, so that path fails
  safe. Enforcement decisions travel through `plugins enable` and `plugins review-update`,
  which a v0.2 panel never invokes in hardened mode at all.

**Overview and bar visibility**

- Add a compact **Protection status** block showing the last successful scan time, analysis
  freshness, CLI version, installed schedule policy, and whether hardened gating is available
  for OmaSafe-controlled enable/update operations. Use “gate available/used,” never
  “protected” or “safe.”
- Keep source drift, analyzer improvement, and enforcement-policy change as three visibly
  distinct event types. A stable plugin commit with a new analyzer result must not inherit the
  source-changed color or wording.
- Render coverage independently from findings: `Complete`, `Partial`, `Unsupported`,
  `Skipped`, `Truncated`, and `Stale` get explicit labels. “No findings” plus anything other
  than complete/current coverage must read as **incomplete review**, not a quiet green state.
- Preserve the count/state badge rather than inventing a risk score. Critical desktop
  notifications remain CLI-owned and independent of the bar widget.

**Findings and coverage views**

- Add filters for new/unchanged result, severity, finding versus capability, and coverage
  state. Default to new/blocking items while retaining one action to show the full report.
- Show “Why blocked” from CLI reason codes, with the exact rule, coverage state, identity, or
  unsupported executable that caused the decision. Do not reduce several blockers to one
  generic failure string.
- Consume `rules coverage` in a read-only coverage drawer: show Baseline V3 relations,
  unresolved gaps, blocking-eligible families, and their measured precision/fixture detection
  evidence. Attribute external-baseline claims and do not imply that mapped coverage is
  equivalence where the relation is `partial-overlap` or `not-covered`.
- Invalidate analysis/decision caches on content digest, analyzer identity,
  enforcement-policy identity, CLI version, override mutation, reviewed update, or a new scan.
  A stale cached report remains labeled stale until refreshed; it never drives an action.
  Today's cache is keyed on plugin ID plus digest only (`Panel.qml:3184-3185`), so the
  identity and version dimensions are a real change to existing behavior.
- **Expiry is a cache dimension, and validity stays CLI-owned.** None of the triggers above is
  wall-clock time, and overrides carry `expires_at`. A cached decision whose basis is an
  override would otherwise stay valid while all seven triggers hold steady, so the panel could
  render an expired override as still authorizing.

  The panel's only job here is *staleness*, never *validity*: once `expires_at` passes, mark
  the cached decision stale and refresh it from the CLI, then render whatever the CLI returns.
  The panel may display time remaining as a convenience, but it must not independently
  conclude that an override has lapsed — override validity is CLI-owned like every other
  policy evaluation, and a QML-side expiry verdict would breach the same consumer boundary
  this slice sets everywhere else.

  Test it as the full sequence — warm cache → expiry passes → marked stale → CLI refresh →
  CLI reports expired. An acceptance test that only exercises a fresh evaluation passes while
  the bug remains.

**Plugin lifecycle controls**

- Add explicit Advisory/Hardened selection to the reviewed-update confirmation. Before
  mutation, show the exact commit/content digest, expected coverage requirements, and that
  hardened mode may block re-enable. Never persist a silent UI-only policy default that
  differs from the argv passed to the CLI.
- For already inactive plugins, offer the CLI-owned hardened enable preflight. Show the H0
  first-install limitation prominently when native inactive staging is unavailable; do not
  label this action a complete install gate.
- On a blocked whole-bar update, show that the prior trusted revision remains active and keep
  the CLI recovery instructions available. The plugin must not independently disable, switch,
  roll back, or trust a bar/plugin. **Recovery guidance for this case must also reach the
  notification and CLI path, not only the panel:** when the blocked plugin is a third-party
  whole-bar plugin, it suppresses OmaSafe's own bar widget — that is exactly what
  `oma.context.replaces-bar` flags — so panel-only instructions can sit behind a surface the
  user cannot open. Treat whole-bar recovery and notification independence as one linked
  requirement, not two separate acceptance items.
- List active, expired, and near-expiry overrides with their exact binding and reason. Do not
  create overrides from QML: H8a requires an interactive TTY, and same-user panel state is not
  an authorization boundary. The panel may display a copyable exact CLI command, but must not
  execute it or place secrets in it.
- Display schedule state and allow an explicitly confirmed call to `schedule install
  --policy …`; state plainly that the hardened timer scans/reports and does not retroactively
  disable an already-running plugin.

**Consumer safety and failure behavior**

- Reuse bounded argv-only collectors, first-terminal-event latches, timeouts, cancellation,
  and request-generation checks. A late result for plugin A must never render under plugin B
  or authorize B's action.
- Render evidence as bounded plain text only. Never evaluate returned markup/QML, open a
  returned path automatically, interpolate result text through a shell, or display secrets
  beyond the CLI's already bounded/redacted evidence contract.
- An unavailable/old CLI disables only unsupported hardening controls. Navigation, previous
  results marked stale, recovery instructions, and the CLI-independent notification guidance
  remain visible.
- Update the sibling plugin's compatibility document as `docs/cli-v0.2.1-plan.md`; keep its
  current v0.2 tab/process contracts unless the frozen CLI schema requires a targeted change.

**Acceptance**

- Partial/skipped/truncated/stale analysis with zero findings never renders as clean.
- Source, analyzer, and enforcement-policy changes have distinct labels and colors.
- A hardened block shows every CLI reason and advances neither enable state nor trust; a
  blocked `bar` update says the prior revision remains live **and its recovery guidance
  reaches the notification path with OmaSafe's own widget suppressed**.
- Override listings show exact binding/expiry, and no panel path can create an override. An
  override that expires **while its decision sits in cache** is marked stale, refreshed from
  the CLI, and rendered expired on the CLI's authority — the panel never decides validity
  itself.
- An `allow` carrying `authorization_basis: override` is visually distinct from an `allow`
  carrying `authorization_basis: policy`, and still lists its blocking rule IDs.
- A hardened **block**, a failed recovery, and every successful override-authorized enable,
  re-enable, or reviewed update reach the user through the CLI-owned notification path even
  behind a v0.2 panel, and remain recoverable afterwards through `plugins enforcement-status`
  whether or not the notification was seen.
- Scanning, reading status, and listing overrides emit no notification however many overrides
  are active; a suppressed or failing notification daemon does not roll back a transition, and
  its audit event is still retrievable by `audit_event_id`.
- An override used one minute after creation notifies exactly as one used a month later; only
  the displayed age differs.
- Opening the panel adds no second per-plugin invocation sweep beyond the existing status
  queue; Overview reads its last-decision summary from the inventory result.
- Switching selection/tabs during analysis, preflight, schedule status, or rule-coverage load
  cannot apply stale results or lose a running operation.
- The UI works when H8b's blocking-family set is empty and says so without implying hardened
  mode is disabled; precision-independent H8a conditions remain visible.
- Clean-VM tests cover advisory and hardened update, inactive-plugin enable, expired override,
  analyzer-improvement event, policy change, incomplete coverage, native-install residual
  warning, whole-bar block/recovery, unavailable CLI, and notification independence.

## Risks and Mitigations

- **Dataflow scope creep (H4)** → intra-file only, explicit bounds in the ADR, bound
  exhaustion degrades coverage visibly. Cross-file dataflow is v0.3+ scope.
- **New rules outpace precision evidence** → H7 gates H8b; no family becomes blocking without
  measured precision. Capability-first shipping means an imprecise rule costs report noise,
  not a blocked plugin.
- **No family clears its precision threshold** → H8a is deliberately independent of that
  outcome. Hardened mode still blocks on coverage state, identity staleness, unapproved
  executables, and failed postconditions, and H8b ships an empty blocking set rather than
  admitting a family on intuition.
- **H4 changes results under existing baselines** → treat as an analyzer-improvement event
  with its own alert wording, keep trust baselines valid, and surface affected suppressions
  for re-confirmation rather than silently keeping or dropping them. Tested by a baselined
  fixture whose results change across the H4 boundary.
- **H0 reachability answers are negative** → both dependent rules degrade to indicators with
  honest anchors. The slices still ship; only the severity claim changes.
- **Catalog version churn across four detector-bearing slices** → H2, H3, H5, and H6 each
  bump once and record the reason, ending at version 7. H0/H1/H4/H7/H8a/H8b do not bump the
  rule catalog unless they add or redefine catalog content. Users see one released version;
  intermediate bumps are internal to the release.
- **Corpus triage cost (H7)** → the early pass triages only the two families expected to
  qualify for blocking and runs concurrently with H4–H6; remaining families stay audit-only,
  which needs no dispositions to be useful.
- **Hardened mode locks a user out of their own bar** → the pre-enable gate never disables an
  already-trusted plugin; a blocked hardened update on a `bar`-kind plugin blocks the update
  and leaves the prior trusted revision live rather than disabling it; where that is
  impossible the recovery sequence is printed before exit. Overrides remain available, and
  the CLI and desktop-notification paths work with no bar by design.
- **Native first install bypasses the gate** → H0 verifies whether inactive staging exists;
  without it, document the residual risk and pursue the upstream pre-activation hook instead
  of claiming prevention.
- **An already-running plugin forges an override** → remove unattended override creation,
  bind every field exactly, store records privately/atomically, and state that real tamper
  resistance still requires separate authority.
- **The panel becomes a perceived security boundary** → H9 renders CLI-owned decisions and
  uses “gate available/used,” never “safe/protected.” Override creation stays terminal-only,
  and critical notifications remain independent of the bar.
- **CLI/plugin schema drift** → freeze and fixture-test `omasafe.enforcement.v1` as a nested
  addition to `omasafe.report.v1`, render unknown values as unsupported, key caches by both
  identities, CLI version, and decision expiry, and land H9 only after the CLI JSON contracts
  freeze.
- **A v0.2.1 hardened CLI runs behind a v0.2 panel** → the window is guaranteed during the
  sibling-repo lag and unfixable from the plugin side, though a block inside it is conditional
  on hardened mode plus a firing blocker. The old panel still shows findings and a warning
  badge, so the gap is missing enforcement/recovery semantics rather than a false clean state.
  Mitigate by notifying on blocks and failed recovery, and by persisting every decision so
  `plugins enforcement-status` answers after the fact.
- **Expired override renders as still authorizing from cache** → store `expires_at` with the
  cache entry, mark the entry stale once passed, and refresh from the CLI rather than deciding
  validity in QML. Test the full stale → refresh → expired sequence against a warm cache.
