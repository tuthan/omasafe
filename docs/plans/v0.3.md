# v0.3 — Posture Regressions and Update Awareness

Owner: Hung Vo · Size: XL · Dates: set from prior release data

Swapped with AUR review on 2026-09-08: posture moved from v0.4 to v0.3 and AUR/PKGBUILD
review moved to v0.4. The two were independent siblings, so no dependency moved; the swap
places v0.5's remediation and export work directly after the checks it consumes. Size rose
from L to XL when the visibility, support-evidence, and host-schema scope below was added.

## Release Outcome

OmaSafe reports meaningful regressions from Omarchy's expected security posture, pending
updates, and known vulnerabilities affecting installed official packages—without a
universal security score or default root access.

## In Scope

- Read-only checks for updates, vulnerabilities, encryption, firewall/listeners, kernel
  restart state, package trust/inventory, and selected persistence surfaces.
- Explicit complete/incomplete/not-applicable states and coverage explanations.
- Daily quiet scans, regression-focused notifications, and weekly digest.
- An OmaSafe-observed successful-update timestamp through a verified Omarchy post-update
  hook, with missing/unverified state reported as unknown.
- A host-scoped report family and state file: the first OmaSafe data not keyed by plugin.
- A posture panel surface that preserves every check state, its evidence, and why a check
  could not complete.
- A strict-redaction posture export sufficient for support to diagnose an `incomplete`
  result without a round trip, generalized later by v0.5.
- CLI and panel reports plus Markdown/JSON preview foundations for v0.5 export.

## Non-Goals

- Automatic remediation, root helper, hardening installers, or a security grade.
- Treating Secure Boot disabled as a warning on a normal Omarchy installation.
- Treating `systemd-analyze security` as vulnerability evidence.
- Vulnerability claims for arbitrary AUR/foreign packages.

## Check Contract

Each check returns `pass`, `regression`, `attention`, `informational`, `incomplete`,
`not_applicable`, or `error`, plus evidence, observed time, dependencies, and limitations.
The engine distinguishes an unsafe observation from inability to observe it.

Every check has a stable ID that survives wording and implementation changes, and the
catalog carries a version the way `RULE_CATALOG_VERSION` does for rules. Support references
a check by ID across releases, and a renamed check must never silently invalidate a user's
baseline.

That distinction is only real if it survives to the screen. No consumer may render
`incomplete` or `error` as a pass, a neutral state, or an absence. v0.1 already treats lost
coverage as an alert condition rather than a quiet one; host checks inherit that rule.

## Tool Execution Boundary

Posture reads the host through system tools, so a check can be lied to even though nothing
here is privileged and no target-controlled code runs. `omasafe-core::bounds` already pins
stdio, process group, timeout, and output cap; that is necessary and not sufficient.

Resolve every posture tool by fixed absolute path with a cleared or allowlisted
environment. Never inherit `$PATH` for tool resolution. M3 checks for world-writable `$PATH`
entries precisely because they occur, and under that exact condition a shadowed `nft`,
`lsblk`, or `checkupdates` could return a false `pass` — the most damaging failure this
release can have. This mirrors the resolution discipline v0.5's root helper requires;
unprivileged does not mean trustworthy input.

Tool stderr is diagnostic only and never becomes report or panel content, following the
precedent in `omasafe-core::git`, where remote text is deliberately discarded. A tool that
is absent, unreadable, or returns unparseable output yields `incomplete` with the reason
recorded, never a pass and never raw text passed through to the UI.

## Milestones

### M1. Check framework, identity, and host profile

- Add versioned check definitions with stable check IDs, a versioned check catalog,
  bounded subprocess execution, dependency discovery, and deterministic report aggregation.
- Define the host-scoped report schema and state file. Every existing schema and state file
  is keyed by plugin; posture is the first host-scoped family and does not belong inside
  `omasafe.report.v1`. Freeze the field list before M2 consumes it.
- Define collected fields and retention limits before any check reads the host. This moved
  ahead of the checks deliberately: it cannot be a cleanup pass after M2–M4 have already
  built collectors.
- Implement the tool execution boundary above: absolute-path resolution, controlled
  environment, discarded stderr.
- Detect Omarchy/plain Arch context and record relevant versions without collecting
  unrelated machine identifiers.
- Record which tools were found and at what versions. A missing or old tool is the usual
  explanation for `incomplete`, so this is what makes a support report actionable.
- Add fixtureable command adapters so tests never depend on the developer's live system.

Exit: missing commands, denied permissions, timeouts, and malformed output produce
explicit incomplete/error states. A shadowed tool on a writable `$PATH` cannot produce a
pass. The host schema and collected-field list are frozen and documented.

### M2. Update and vulnerability checks

- Run `checkupdates --nocolor` once for pending repository-package inventory and interpret
  its three states: exit 0 with updates, exit 2 after a successful empty check, and exit 1
  on operational failure. It safely runs `pacman -Sy` under `fakeroot` against a temporary
  database; it never syncs the system pacman database.
- For a packaged installation, detect the installed `omarchy` or `omarchy-dev` package and
  filter the successful `checkupdates` result for that exact package.
- Independently handle a development checkout when `$OMARCHY_PATH` is not
  `/usr/share/omarchy`: resolve its configured upstream, perform a bounded noninteractive
  fetch, and compute `HEAD..<upstream>` while preserving missing-upstream, fetch-failure,
  and comparison-failure states. `checkupdates` cannot represent this branch.
- Do not use `omarchy update available` as an authoritative check because it suppresses the
  errors in both native branches and can conflate failure with “up to date.”
- Treat `arch-audit` as an optional official-repository dependency. Missing tool/data is
  `incomplete`, never pass; offer transparent installation guidance and state that AUR
  packages are outside its advisory coverage. This check subsumes the brainstorm's
  separate security-news-feed idea.
- Install the exact `post-update` hook type, directly self-test the OmaSafe hook script
  without firing other user hooks, verify its private atomic stamp, and treat no verified
  stamp as `unknown` rather than “never updated.”
- Make the only full-update recommendation `omarchy update`. Never recommend bare
  `pacman -Sy`, direct system-database synchronization, or bypass of the Omarchy workflow.
- Where pacman logs are readable, report a system database sync apparently not followed by
  a full upgrade as attention with explicit uncertainty; do not confuse `checkupdates`'s
  temporary database with a system sync.

Exit: offline, stale-database, no-update, pending-update, vulnerable-package, and tool-
missing states are distinguishable.

### M3. Core posture checks

- Walk the block-device ancestry for `/` to detect LUKS rather than relying on one
  `lsblk` row.
- Inspect effective nftables/ufw policy, bound addresses, and listening ports; label
  process attribution incomplete when permissions hide owners. Recognize ports 22 (SSH)
  and 53317 (LocalSend) as Omarchy defaults, but evaluate them contextually against actual
  listeners and user expectation rather than declaring them inherently safe.
- Compare running and installed kernels using Omarchy-compatible logic.
- Inventory foreign packages and keyring state without calling foreign packages unsafe.
- Check world-writable `$PATH` entries and selected persistence locations.

Exit: checks are tested against encrypted/unencrypted, firewall frontend variations,
container rules, IPv4/IPv6, permission-limited sockets, and multiple kernel packages.

### M4. Optional informational checks

- Report Secure Boot state without warning by default.
- Prefer `bootctl`/firmware state available on the base system; treat optional `sbctl` or
  `mokutil` as additional evidence, never required dependencies.
- Add SSH configuration review only when sshd is enabled.
- Add scheduled, explicitly labelled `pacman -Qkk` integrity metadata checks.
- Keep `systemd-analyze security`, DNS-over-TLS, AppArmor, and similar opinionated controls
  in opt-in profiles.

Exit: normal Omarchy defaults produce a quiet report rather than pressure to alter the
supported configuration.

### M5. Baselines, scheduling, and notifications

- Reuse v0.1 baseline/review/rebaseline/exclusion behavior for persistence surfaces.
- Extend the shipped `schedule install|uninstall|status` surface, `omasafe.schedule.v1`,
  and `schedule.json` for the daily posture run; add weekly digest generation. This is not
  new scheduling infrastructure.
- Notify only on new high-impact advisories, critical regressions, or repeated scan
  failure; deduplicate unchanged results.
- Map the brainstorm's network snapshot to this listener/process view instead of creating
  a separate duplicate feature.

Exit: a stable machine remains quiet across repeated scans; a controlled regression
produces one evidence-backed notification and a clear review path.

### M6. Retention and performance hardening

- Enforce the M1 retention limits and prune history deterministically.
- Keep raw process arguments, usernames, network peers, and sensitive file contents out
  of reports unless explicitly requested for a local diagnostic export.
- Benchmark quick/daily/weekly profiles and enforce per-check budgets.

### M7. Visibility, support evidence, and release

- Add a posture panel surface showing, per check: state, evidence, observed time, the tool
  or dependency used, and the coverage explanation when a check did not complete. This is
  the host analogue of v0.1 M6's identity/baseline/changed-files/cache-age/limitations list.
- Keep the bar to an alert count or state, never a grade or "safe" badge. Treat the badge
  as a convenience, not the sole channel: when a non-built-in full bar replaces the bar and
  omits the OmaSafe widget, posture regressions must remain observable through the CLI and
  desktop notifications, matching v0.1's requirement for drift alerts.
- Define the pre-first-scan state and a result-age indicator. Posture is scheduled, so the
  panel must distinguish "not yet run" from "clean" and show staleness the way v0.1 shows
  cache age and v0.2.3 shows cached/stale hydration.
- Ship read-only remediation guidance per check: a copyable next step or documentation
  link. v0.5 owns the actions themselves, so without this the user sees a regression with
  no path forward for a full release cycle. Nothing in this milestone mutates host state.
- Add a strict-redaction posture export carrying check results, host context, tool
  inventory and versions, schema and check-catalog versions, and coverage limitations.
  `provenance --format json` and `paths` already supply part of this; reuse them rather
  than duplicating. v0.5 M4 generalizes the redaction levels.
- Coordinate the host-scoped schema with the sibling plugin repository before release, the
  way v0.2.4's consumer gate did. Record the sibling commit or explicitly retain legacy
  consumer behavior; an older plugin must never render an unknown check state as a pass.
- Document unsupported host configurations and false-positive handling.

Exit: every check state reaches the user with its evidence and its reason; critical
posture alerts survive a third-party full bar; support can diagnose an `incomplete` result
from one exported artifact.

## Success Metrics

- 100% correct classification of `checkupdates` success-with-updates, success-empty, and
  operational-failure fixtures.
- 100% correct classification of packaged and development-checkout Omarchy update fixtures,
  including missing upstream and failed fetch.
- Zero permission/tool failures reported as pass.
- Zero repeat notifications for an unchanged machine across seven daily fixture runs.
- 100% of default exported/check state fixtures contain no raw secret values.
- 100% of `incomplete` and `error` fixtures render as a distinct non-passing state in every
  consumer, including a plugin build older than the current check catalog.
- 100% of critical posture-alert fixtures remain observable when a third-party full bar
  replaces the bar, matching v0.1's drift-alert metric.
- Every `incomplete` fixture names the missing tool, denied permission, or timeout that
  caused it, in both the panel and the export.
- Zero posture tools resolved through an inherited `$PATH` across the shipped check set.

## Test Matrix

- Command-output fixtures for every supported version and failure state.
- Permission-limited user, no network, `checkupdates` exits 0/1/2, missing optional tools,
  stale sync database, packaged/development checkout, missing Git upstream, fetch failure,
  ambiguous native Omarchy status, and interrupted hook writes.
- LUKS/LVM/Btrfs/multi-device root layouts.
- ufw/nftables, Docker/container rules, IPv4/IPv6 listeners, and localhost-only services.
- New/acknowledged/excluded persistence changes and notification deduplication.
- Privacy snapshots verifying that default reports contain no secret values.
- A writable `$PATH` entry shadowing `nft`, `lsblk`, and `checkupdates` with binaries that
  report a clean host; the affected checks must not pass.
- Every check state rendered in the panel, plus pre-first-scan, stale-result, and
  check-catalog-newer-than-consumer states.
- Built-in and third-party full bars, including a replacement that omits the OmaSafe widget.
- Support-export fixtures for a missing optional tool, a denied permission, and a timeout.

## Acceptance Criteria

- OmaSafe never syncs the system pacman database directly; the documented temporary-
  database `checkupdates` implementation is allowed and tested.
- Bare system `pacman -Sy` is never recommended.
- Update counts and Omarchy update availability are not conflated.
- Package and development-checkout update paths retain independent failure states.
- Normal Omarchy Secure Boot, LUKS, and firewall defaults are interpreted correctly.
- Permission/tool failures cannot appear as passing checks, in the engine and in every
  consumer that renders them.
- Stable machines are quiet; regressions and relevant new advisories are actionable.
- Default operation requires no root privileges.
- Posture tools resolve by absolute path under a controlled environment, and tool stderr
  never reaches a report or the panel.
- Check IDs are stable across the release; a renamed or reworded check does not invalidate
  a user baseline without an explicit migration.
- Host-scoped posture data lives in its own schema and state file, not inside the
  plugin-scoped report family.
- Every regression the panel shows carries a read-only next step; v0.3 mutates no host
  state.
- A support export reproduces a check result with enough host and tool context to explain
  an `incomplete` without further questions.
