# v0.5 — Controlled Remediation and Reporting

Owner: Hung Vo · Size: XL · Dates: set from prior release data

## Release Outcome

OmaSafe can perform a small, audited set of explicit hardening actions through polkit,
starting with one high-value installer, and can export privacy-reviewed posture/trust
reports. Read-only operation remains the default.

## In Scope

- A root-owned, non-daemon helper with fixed action IDs and typed arguments.
- Separate polkit policy/actions for the first approved remediations.
- OpenSnitch as the first hardening installer/configuration workflow.
- Report export as Markdown and JSON with selectable redaction levels.
- Advanced drift targets whose value was validated in v0.2/v0.4.
- Rollback/uninstall behavior for every OmaSafe-applied change.

USBGuard and fail2ban are stretch goals for v0.5.x after the helper and OpenSnitch path
have been audited in real use.

## Non-Goals

- A general root command runner, shell proxy, persistent privileged daemon, or NOPASSWD.
- Automatic remediation or background privilege prompts.
- Running `omarchy update` through the helper; updates remain an interactive
  `omarchy update` workflow in a terminal.
- ClamAV, AIDE, panic isolation, secrets scanning, or compliance certification.

## Privileged Boundary

The UI requests a named operation such as `opensnitch.install` through the unprivileged
CLI. The root-owned helper independently validates the action ID, exact argument schema,
caller context, current system state, and allowed paths. It constructs argv internally,
uses a minimal fixed environment, and never accepts shell text, an executable path, or
arbitrary files from QML.

Each materially different operation gets an appropriate polkit action and description so
the authentication prompt states the real effect.

Omarchy's polkit agent and lock/PAM UI share the same unsandboxed shell process as
third-party plugins. Therefore QML and the rendered prompt are not trusted enforcement
boundaries. Security rests on the root-owned polkit policy/helper accepting only the fixed,
bounded effect named by the prompt. OmaSafe must disclose this limitation, surface
unreviewed plugin drift before remediation, and track the shared-process architecture as an
upstream Omarchy concern.

## Milestones

### M1. Privilege threat model and helper skeleton

- Write a source-to-sink threat model covering QML compromise, CLI argument forgery,
  shared-process polkit/lock UI compromise, prompt spoofing, CLI argument forgery,
  environment injection, PATH substitution, symlink races, TOCTOU, and partial failure.
- Define the action registry and typed schemas in code, not configuration writable by the
  invoking user.
- Resolve root-owned executables by fixed absolute path and clear/allowlist environment.
- Add structured audit events without secrets.
- Verify that third-party plugins cannot expand the helper's fixed root effects even if
  they can request an action or interfere with the shell-rendered prompt.

Exit: unknown actions, extra arguments, hostile environment, symlinked state, and
concurrent requests are rejected before mutation.

### M2. Preview/execute/verify/rollback transaction model

- Every action implements idempotent `inspect`, `preview`, `execute`, `verify`, and where
  feasible `rollback` operations.
- Bind approval to a digest of the previewed action/arguments so the executed request
  cannot differ from what the user saw.
- Record only OmaSafe-owned change metadata needed for verification/removal.
- Recover clearly from package-manager lock, network failure, cancellation, and reboot.

Exit: repeated execution is safe and interrupted operations report a recoverable state.

### M3. OpenSnitch workflow

- Detect installed/running/configured state before offering installation.
- Explain tradeoffs, package sources, services, expected prompts/noise, and removal.
- Install through approved Omarchy/package mechanisms where compatible, then apply the
  smallest documented baseline configuration.
- Verify service state and expose a rollback/uninstall path that does not delete unrelated
  user rules.

Exit: install, already-installed, partial, failed, verify, and uninstall scenarios pass in
an Omarchy VM.

### M4. Privacy-aware report export

- Add `report export --format markdown|json --redaction strict|standard|diagnostic`.
- Default to strict redaction: no usernames, raw secret values, peer addresses, complete
  process command lines, or absolute home paths.
- Include tool/schema versions, scan times, coverage, baselines, acknowledged exceptions,
  and clear “not a certification” language.
- Preview the exact export before writing or copying it.

Exit: golden exports are stable, useful, and pass automated sensitive-data fixtures.

### M5. Advanced drift targets

- Add only targets validated as useful during v0.2/v0.4, such as systemd user units,
  autostarts, shell startup files, and selected pacman hook directories.
- Preserve file-level review/rebaseline/exclusion and avoid storing file contents when a
  digest plus safe metadata is enough.
- Require elevation only for a user-requested deeper read; default scans remain unprivileged.

### M6. Audit and release

- Security-review the helper and polkit policy separately from the UI.
- Fuzz action decoding and argument validation.
- Test package upgrades/downgrades and helper/CLI version mismatch (fail closed).
- Document all root-owned files and exact uninstall cleanup.

## Success Metrics

- Zero accepted unknown actions, extra arguments, caller-selected executables, or hostile
  environment values across fuzz/property tests.
- 100% of mutating actions implement and pass inspect/preview/execute/verify plus documented
  rollback or explicit non-rollback semantics.
- Zero fixture secrets in strict/default exports.
- Clean install, interrupted action recovery, upgrade, and uninstall pass in the VM harness.

## Test Matrix

- Compromised-QML simulations requesting unknown actions, injected args, hostile PATH and
  locale, oversized input, symlink targets, and request races.
- Polkit allow/deny/cancel, noninteractive invocation, missing agent, and stale approval.
- Package-manager locks, mirror failure, partial installation, verification failure, and
  rollback.
- Export redaction with API keys, home paths, usernames, network addresses, and command
  lines embedded in fixtures.
- CLI/helper version skew and corrupted action state.

## Acceptance Criteria

- No arbitrary string from QML can become a privileged command, executable, path, or
  environment value.
- Privileged operations are fixed, previewed, explicitly approved, verified, and
  idempotent.
- Read-only scans never trigger polkit.
- OpenSnitch changes can be identified and reversed without deleting unrelated user data.
- Default exports contain no fixture secrets and clearly describe coverage/limitations.
- Removing OmaSafe removes its helper/policy/state as documented and leaves user-managed
  security tools/configuration intact unless explicitly removed.
