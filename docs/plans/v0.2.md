# v0.2 — Payload-Aware Plugin Capability Analysis

Owner: Hung Vo · Size: XL · Dates: set from v0.1 delivery data
Execution sequence: [v0.2-implementation.md](v0.2-implementation.md) (vertical slices S0–S8)

## Release Outcome

OmaSafe augments v0.1 provenance and diff with deterministic, evidence-backed analysis of
the entire relevant plugin payload. It inventories QML, JavaScript, shell, Python,
extensionless executables, and binary files; prioritizes invocation/data-access edges; and
explains coverage without declaring a plugin safe or malicious.

A reviewed-update workflow scans the candidate commit before modifying the enabled plugin.

## In Scope

- Safe ingestion of installed trees, local directories, immutable Git revisions, and URLs.
- Full shipped-payload inventory with file type, mode, size, digest, and coverage state.
- Detection of QML-to-bundled-payload invocation/reference edges.
- QML-aware parsing and embedded JavaScript analysis with explicit lexical fallback.
- Minimal high-signal shell/Python lexical rules; unparsed behavior remains an explicit
  coverage limitation pending deeper language analyzers.
- Sensitive shared-shell APIs: process/filesystem/network, polkit, PAM/session lock,
  Wayland/Hyprland control, clipboard, timers, and background services.
- OmaSafe-owned rules with versioned Marketplace Baseline V3 equivalence mappings where
  semantics are identical.
- Versioned reports, analysis fingerprints, rule policy identity, suppressions, and UI.
- Exact-candidate preflight followed by native `omarchy plugin update` mutation,
  validation, rollback-on-native-validation-failure, and rescan.

## Non-Goals

- Runtime sandboxing, behavioral detonation, network interception, or malware verdicts.
- Complete semantic understanding of arbitrary shell/Python/binary payloads.
- Replacing the marketplace's listing-time baseline or claiming official affiliation.
- Automatically trusting or updating a plugin.
- AUR/PKGBUILD, posture, agent configuration, browser extensions, or root actions.

## Analysis Identity Model

v0.2 adds two identities beside v0.1 source identity:

- **Analysis fingerprint:** sorted normalized results such as rule/capability ID, relative
  evidence path/location fingerprint, and semantic value. It excludes timestamps, prose,
  excerpts, temporary paths, and tool build version.
- **Policy identity:** analyzer/rule catalog version, parser versions, configured limits,
  severity-table version, external-equivalence-map version, and supported Omarchy
  security-surface version.

Events are classified separately:

- Source identity changed → plugin drift.
- Source unchanged and policy changed → analyzer updated; re-evaluation, not plugin drift.
- Source and policy unchanged but fingerprint changed → nondeterminism/error.
- Severity or rule meaning changes require a new policy identity.

## Initial Capability and Rule Priorities

1. QML invokes a bundled executable/script or a mutable external command.
2. Access to polkit, PAM/session-lock, authentication UI, or lock-surface APIs.
3. Process/shell execution, sensitive filesystem access, network, clipboard monitoring,
   service management, and persistence.
4. Bundled executable binaries and unsupported executable payloads.
5. Dynamic code construction, encoded/obfuscated payload indicators, and computed sinks.

Plugin kind affects review priority and context, not severity by itself. `service` and
whole-`bar` plugins receive dedicated corpus coverage because they are headless or replace
critical UI, but bar widgets run in the same unrestricted process. Every third-party
whole-bar report discloses `replaces the bar`, because it can suppress OmaSafe's ambient
badge even when no security finding is present.

## Milestones

### M1. Versioned Omarchy security-surface inventory

- Maintain [`reference/omarchy-security-surface.md`](../reference/omarchy-security-surface.md)
  with tested Omarchy/Quickshell versions and reachable sinks.
- Reverify imports, plugin loading, polkit agent, lock/PAM service, and IPC per supported
  Omarchy release.
- Convert sensitive APIs into stable capabilities/rules with evidence requirements.
- Document explicitly that manifest path containment is not runtime sandboxing.

Exit: every high-priority rule maps to a verified sink or payload edge and a supported
version range.

### M2. Safe target ingestion and payload inventory

- Reuse v0.1 local/Git identity and untrusted-input limits.
- For remote targets, read Git objects without hooks, checkout filters, submodules, LFS,
  project tooling, or target-controlled code execution.
- Inventory every relevant file and mode, including QML/JS, shell, Python, executable
  extensionless files, ELF/PE/Mach-O indicators, and unsupported binaries.
- Resolve QML literal/local-path references to payload files without following symlinks or
  leaving the logical repository root.
- Make skipped, truncated, unsupported, or unreferenced payload coverage visible.

Exit: a plugin whose QML invokes a bundled Python/shell executable cannot produce an
apparently clean report merely because that payload language is not parsed.

### M3. QML parser decision and kill criterion

- Evaluate `tree-sitter-qmljs` as the primary error-tolerant parser with byte/line spans.
- Use `qmllint --json` as an optional correctness/import signal, not the capability engine.
- Keep QQmlSA documented as a future type-aware option, not a v0.2 dependency.
- Measure parser coverage against pinned marketplace entry points and relevant QML files.
- Kill criterion: if fewer than 99% of entry-point QML files or 95% of all relevant QML
  files parse without material uncovered regions, parser-dependent conclusions ship as
  explicitly lexical/lower-confidence rather than silently claiming AST coverage.

Exit: parser choice, measured coverage, unsupported syntax, and fallback behavior are
recorded in an ADR and report metadata.

### M4. Deterministic report and rule contract

- Implement the shared report envelope from [README.md](README.md).
- Emit target source identity, analysis fingerprint, policy identity, payload inventory,
  capabilities, findings, evidence, and coverage limitations.
- Add stable rule explanations and explicit scoped suppressions with human reasons.
- Use deterministic code for all automated outcomes; LLM output can never change severity,
  finding presence, enforcement, or trust state.
- Return success when analysis completed even with findings; CI uses
  `--fail-on <severity>` explicitly.
- Add a determinism canary: unchanged source identity and policy identity must yield the
  same analysis fingerprint; any mismatch fails CI with preserved repro inputs.

Exit: a tool-version/prose-only bump preserves analysis fingerprint, a policy change is
labelled analyzer improvement, and unchanged source/policy produces identical results.

### M5. Marketplace compatibility and validator parity

- Keep stable OmaSafe-owned rule/capability IDs. Record compatible Marketplace rules in a
  mapping containing external system, external rule-set version, external rule ID, and the
  version/commit against which equivalence was verified.
- Mark a mapping stale and require review when the external rule definition/version moves;
  never let upstream vocabulary silently redefine severity or finding meaning.
- Consume the marketplace's deterministic fixture corpus where licensing permits.
- Implement Omarchy manifest checks for plain Arch use, but add a CI canary that runs both
  OmaSafe and `omarchy plugin validate <folder>` over the pinned corpus.
- Fail the compatibility build on disagreement for the recorded Omarchy version; at
  runtime, an unverified newer Omarchy version degrades validator coverage rather than
  silently passing.

Exit: overlapping results use one vocabulary and manifest-validator drift is caught before
release.

### M6. Capability analyzers

- Detect process/network/filesystem/clipboard/background/dynamic-code capabilities in QML
  and embedded JavaScript.
- Detect literal and normalized QML → local payload invocation edges first.
- Add minimal shell/Python lexical rules only for high-signal constructs; label those files
  partially analyzed and do not infer clean behavior from no match.
- Add near-zero-legitimacy third-party rules for direct polkit-agent, PAM/session-lock, and
  lock-surface access, with careful evidence and manual triage.
- Separate capability from suspicious finding: process execution alone is not malicious.

Exit: every result has stable ID, evidence, explanation, confidence, remediation/review
guidance, and accurate language-level coverage.

### M7. Pinned real-plugin corpus and false-positive budget

- Build a reproducible corpus manifest from the 653-community-plugin catalog snapshot,
  pinning each entry by its `upstreamObservedCommit` plus repository, layout, manifest
  path, and expected availability.
- Store dispositions as in-repository expectation files keyed by
  `{plugin_id, commit, rule_id}` so the corpus is both triage ledger and regression fixture.
- Run a representative pinned subset on every PR and the full pinned corpus nightly/release.
- Publish per-rule true-positive, false-positive, untriaged, and incomplete counts.
- Gate release on zero known high-severity false positives and zero untriaged high-severity
  results—not zero genuine high findings.
- Treat live-catalog refresh as a separate scheduled compatibility job, never deterministic
  PR input.

Exit: high-severity policy has an auditable corpus record and incomplete repos cannot be
counted as clean.

### M8. Reviewed update workflow

- Add `omasafe-cli plugins review-update <id>`.
- Fetch the candidate into OmaSafe's bounded cache, correlate its exact commit with the
  pinned registry claim, run OmaSafe and native manifest validation, and show the delta
  from the trusted baseline—not merely native updater's current-HEAD text diff.
- Require a clean installed worktree before delegation. Refuse and offer review guidance
  when local edits exist, because the native validation-failure rollback uses
  `git reset --hard ORIG_HEAD` and must not erase unrelated work.
- Require explicit approval, then disable an ordinary enabled plugin or switch a full
  `bar` plugin with `omarchy bar use omarchy.bar` before mutation.
- Delegate live fetch/fast-forward, native validation, native validation rollback, and
  `rescanPlugins` to `omarchy plugin update <id> --yes`; do not fork its lifecycle logic.
- Propose an upstream expected-commit option so the native updater can refuse when fetched
  `HEAD` differs from the reviewed SHA. Until that exists, state the limitation explicitly:
  the inactive working tree can receive a raced commit, but it cannot be re-enabled or
  trusted without an exact postcondition match.
- After the native command, require installed `HEAD` to equal the exact reviewed commit and
  re-run OmaSafe analysis. A raced/different commit or failed postcondition remains
  disabled/on the built-in bar and is never trusted or automatically re-enabled.
- Restore prior enabled/bar configuration only after exact-commit and analysis
  postconditions pass, then record the explicit trust decision. Preserve interrupted-state
  recovery and clear manual recovery guidance for failures the native command cannot undo.
- Continue detecting native updater use after change; never assume all users route through
  OmaSafe.

Exit: rejected candidates never modify the live tree; accepted mutations use the native
updater; only the reviewed commit can be re-enabled/trusted; native validation failures use
native rollback and all other postcondition failures remain inactive with recovery guidance.

### M9. CLI, UI, packaging, and release

- Provide `scan-plugin`, `rules list/explain`, payload/evidence views, cancellation, and
  bounded JSON/text output.
- Extend the panel with capability, payload, invocation-edge, finding, confidence, and
  coverage views.
- Require signed tags/artifacts, verification instructions, a published self-scan, corpus
  report, validator-parity report, and clean-VM lifecycle tests.

## Success Metrics

- 100% of relevant shipped files receive an inventory/coverage state.
- ≥99% entry-point and ≥95% all-QML parser coverage, or explicit reduced lexical claims.
- Zero known high-severity false positives and zero untriaged high-severity corpus results.
- Zero unexplained fingerprint changes for identical source/policy inputs in CI.
- 100% agreement with native manifest validation for the recorded supported Omarchy
  corpus/version.
- Every QML-to-bundled-executable fixture exposes the invocation edge.

## Test Matrix

- QML objects, inline handlers, imported JS, computed properties, comments, malformed
  syntax, and lexical fallback.
- Bundled Python/shell/extensionless/native binaries, mode-only executable changes, and
  indirect/local path references.
- Process, FileView, network, clipboard, timer/service, polkit, session-lock, PAM, Wayland,
  and Hyprland sink fixtures.
- Marketplace baseline overlap, positive/negative/boundary fixtures, and validator parity.
- Expectation-file additions/removals, stale external-rule mappings, and determinism-canary
  mismatch reproduction.
- Parser/tool/policy version changes versus unchanged source identity.
- Resource exhaustion, traversal, symlink, submodule, LFS, credentialed URL, huge file,
  malformed UTF-8, binary, and timeout cases.
- Reviewed update reject, disabled/active service, full bar, dirty tree, invalid manifest,
  validation failure, rescan failure, and interrupted rollback.

## Acceptance Criteria

- No target-controlled code executes during ingestion or analysis.
- Every relevant payload is inventoried even when its language is unsupported.
- No report interprets “not parsed/no match” as clean behavior.
- Sensitive shared-shell capabilities are visible with evidence and versioned provenance.
- Analyzer changes and source drift are distinct events.
- Corpus and validator gates pass with published results.
- Mutation starts only after exact-candidate review and approval; because today's native
  updater lacks an expected-SHA guard, the plugin remains inactive until installed `HEAD`
  exactly matches that candidate and all postconditions pass.
- The wrapper never invokes the native updater on a dirty installed worktree.
- Documentation never claims runtime sandboxing, safety proof, or official affiliation.
