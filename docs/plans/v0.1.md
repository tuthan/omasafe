# v0.1 — Local Plugin Trust and Drift

Owner: Hung Vo · Size: L · Dates: set after M0 establishes delivery capacity

## Release Outcome

OmaSafe answers four questions without needing a static analyzer:

1. Which third-party plugins are installed, and what exact Git/tree revision is present?
2. Is each plugin listed in the independent marketplace?
3. Does the installed commit match the marketplace's listing-validated commit?
4. What source changed since the user established a trust baseline?

The CLI provides inventory, correlation, trust, and diff workflows. A thin Omarchy panel
shows the same local state and alerts only on new drift or lost coverage.

## In Scope

- Inventory from `omarchy plugin list --json`, the user plugin directory, and Git metadata.
- Cached, schema-validated consumption of marketplace `catalog.json` pinned to a recorded
  catalog-repository commit and treated as untrusted data.
- Correlation of installed, listing-validated, upstream-observed, and user-trusted commits.
- Git commit/tree identity plus a normalized digest for local/dirty plugin content.
- Human-readable source diffs independent of security rules.
- Explicit trust, review, acknowledge/rebaseline, history, and scoped exclusions.
- Detection of changes made by direct edits or native `omarchy plugin update`.
- Detection and disclosure when a non-built-in `bar` plugin replaces the entire bar.
- Daily systemd user scan, shell-independent critical notifications, and a thin
  bar-widget/panel UI.

## Non-Goals

- Static capability or malware analysis.
- Declaring a listed, verified, unchanged, or trusted plugin safe.
- Intercepting or blocking native Omarchy updates before activation.
- A pre-activation analyzer/native-updater wrapper; that requires v0.2 analysis and review
  policy.
- AUR, machine posture, agent configuration, browser extensions, or privileged actions.

## Identity Model

Keep these identities separate so a tool upgrade cannot masquerade as plugin drift:

- **Source identity:** plugin ID, normalized repository URL, `HEAD` commit, Git tree OID,
  and current normalized working-tree digest.
- **Registry identity:** catalog generation time, verification status,
  catalog-repository commit/file digest/retrieval time, `listingValidatedCommit`,
  `upstreamObservedCommit`, verification-status claim, and upstream-check claim.
- **Trust identity:** exact source identity the user accepted, acceptance time, note, and
  previous trust history.

v0.2 adds a separate analysis fingerprint and policy identity. Neither becomes part of
the source identity.

## Drift Target Model

Define the shared collector boundary in v0.1:

`collect() -> { target_id, paths, digest, classification, coverage }`

The baseline engine, history, acknowledge/rebaseline, scoped exclusions, and notification
deduplication operate on this result. The common baseline is digest-only and never stores
file contents, which keeps later secret-bearing targets from leaking values into state.
Only the installed-plugin collector is registered in v0.1; agent, persistence, and browser
collectors remain out of scope.

## Marketplace Interpretation

- `verified` means the recorded marketplace snapshot claims its deterministic policy
  accepted or explicitly reviewed the exact listing commit; it is not a local fact or a
  security guarantee.
- `unverified` does not mean malicious.
- “Upstream moved” means the remote branch advanced beyond the listing commit; it does not
  prove the installed tree changed.
- “Unlisted” means no catalog entry matched the plugin ID/repository; it does not prove
  maliciousness, but no marketplace listing-time result applies.
- Offline/stale catalog state is always visible and never silently treated as current.
- Registry claims can add context but never suppress or downgrade local drift or coverage.

## Milestones

### M0. Project and reproducible test infrastructure

- Initialize Git and commit the reviewed documentation before implementation begins.
- Create the Rust workspace, CLI skeleton, error model, XDG state/cache modules, and tests.
- Provision a snapshot-capable Omarchy VM harness for install, upgrade, removal, shell-
  stopped, and shell-running tests.
- Record tested Omarchy/Quickshell versions in generated coverage metadata.
- Record sustainable maintainer hours per week before assigning delivery dates.

Exit: CI runs unit tests and a repeatable smoke workflow against a clean Omarchy snapshot.

### M1. Installed inventory

- Add `omasafe-cli plugins inventory [--format text|json]`.
- Parse `omarchy plugin list --json` when the shell is available, but continue from the
  filesystem when it is stopped.
- Reconcile shell IDs with `~/.config/omarchy/plugins/` without following symlinks.
- Record the active full-bar ID and whether a non-built-in plugin replaces `omarchy.bar`.
- Distinguish built-in, cloned/local, Git-managed, backup, malformed, and unscannable
  directories.
- Derive repository URL/commit from Git because Omarchy's list output omits them.

Exit: fixtures cover enabled/disabled, stopped shell, dirty checkout, detached head,
missing remote, backup directory, malformed manifest, symlink, and non-Git plugin.

### M2. Marketplace catalog correlation

- Resolve and record a GitHub catalog-repository commit, fetch `site/catalog.json` by that
  immutable commit, verify its digest, then perform bounded atomic cache replacement.
- Treat every catalog field as untrusted display/input data.
- Support `root-plugin`, `monorepo`, and `suite` layouts explicitly; preserve unknown
  layouts as incomplete rather than guessing.
- Correlate by plugin ID plus normalized repository identity, detecting conflicting IDs or
  repositories instead of selecting the first match.
- Show listed/unlisted, verified/unverified, installed-versus-validated, and
  upstream-moved states with the marketplace disclaimer.
- Retain the last good snapshot for offline use and display its age/generation time.
- Attribute verification and upstream status to the exact registry commit and retrieval
  time; never let a registry claim clear a local signal.
- Detect an older/non-descendant catalog revision relative to the last observed snapshot
  and surface it as registry rollback/conflict rather than silently replacing history.

Exit: the 2026-08-20 catalog snapshot (689 entries, 653 community) parses within limits,
and malformed/oversized/conflicting/offline cases fail visibly without losing the cache.

### M3. Source identity and trust baseline

- Compute immutable commit/tree identity for clean Git checkouts and a normalized content
  digest for local changes/non-Git plugins.
- Normalize paths, modes, and relevant file ordering without following symlinks.
- Add `plugins trust <id>` with an interactive identity/catalog review.
- Refuse unattended trust unless exact expected identity and an explicit flag are given.
- Store private, atomic, versioned history under the XDG state directory.
- Implement the generic drift-target result and digest-only baseline storage with only the
  plugin collector registered.

Exit: timestamps, tool version, message wording, and catalog refresh do not change source
identity; a relevant byte/mode/path change does.

### M4. Diff and review workflow

- Add `plugin diff <id> [<ref-a>..<ref-b>]` and `plugin status <id>`.
- Show commit metadata, file status, bounded text diffs where immutable Git objects are
  available, binary/mode changes, renames, and omitted/unavailable content due to limits.
- Compare trusted versus installed identity by default, even when no rule understands the
  changed content.
- Add review, acknowledge/rebaseline, restore-previous-baseline, and scoped exclusion.
- Require a reason and scope for exclusions; never make “accept revision” equivalent to
  “ignore future changes.”

Exit: source changes remain reviewable even when files are binary, unsupported, or
intentionally obfuscated.

### M5. Drift scheduling and native-update detection

- Install an opt-in systemd user timer for daily inventory/identity checks.
- Detect native `omarchy plugin update` and direct editor changes after they modify the
  live tree; label this as post-change detection.
- Notify only on source drift, missing/unscannable plugin, conflicting provenance, or lost
  coverage; debounce rapid editor writes and deduplicate unchanged alerts.
- Deliver critical notifications from the scheduled CLI through the desktop notification
  service, independently of whether OmaSafe's bar widget is rendered.
- Never imply that users must route updates through OmaSafe in v0.1.

Exit: a stable machine is quiet; one controlled change produces one alert and review path.

### M6. Thin Omarchy UI

- Create a valid `bar-widget`; `BarWidget.qml` loads the nested `Panel.qml`.
- Invoke only fixed inventory/status/diff/trust subcommands with argv-style arguments.
- Show installed identity, marketplace correlation, baseline, changed files, cache age,
  and coverage limitations.
- Keep the bar to an alert count/state—never a grade or “safe” badge.
- Treat the bar badge as a convenience, not the sole alert channel. When a third-party full
  bar is active, show “replaces the bar” in status and keep CLI/desktop-notification review
  available even if that bar does not host OmaSafe's widget.

Exit: validation, `qmllint`, click/open/close, stopped CLI, corrupt state, shell restart,
disable/re-enable, and removal workflows pass.

### M7. Packaging, signing, and release

- Provide Arch packaging, man pages, shell completions, and documented install/removal.
- Require signed source tags and signed release artifacts with a verification procedure.
- Publish a deterministic self-inventory/provenance report.
- Test clean install, upgrade, downgrade where supported, and uninstall in the VM harness.

## Success Metrics

- 100% of readable Git-managed installed plugins receive commit/tree identity.
- ≥99% correct catalog correlation on the frozen 2026-08-20 catalog fixture; all ambiguous
  matches are surfaced, never guessed.
- Median scheduled-change-to-local-alert time under 24 hours; immediate manual scan works.
- Zero alerts when only OmaSafe tool/message versions change and plugin source is unchanged.
- 100% of critical-alert fixtures remain observable when a third-party full bar is active.

## Test Matrix

- Shell running/stopped and current/older supported Omarchy output.
- Clean, dirty, detached, force-updated, removed, unlisted, and locally edited plugins.
- Root, monorepo, suite, conflicting ID/repository, and unknown layouts.
- Catalog timeout, offline, stale, malformed, oversized, duplicate, and rollback states.
- Path traversal, symlinks, special files, malformed UTF-8, huge/binary files, and mode-only
  changes.
- Concurrent scans, interrupted atomic writes, corrupted/truncated state, and baseline
  history recovery.
- Notification deduplication, acknowledgement, exclusion, and trust rollback.
- Built-in and third-party full bars, including a replacement that omits the OmaSafe widget.

## Acceptance Criteria

- Inventory and diff never execute plugin or catalog-controlled code.
- Unchanged source remains unchanged across an OmaSafe version bump.
- Registry status is commit-bound and always shown with age/limitations.
- Registry claims never downgrade or suppress local drift or lost coverage.
- No baseline is created implicitly.
- Direct/native changes are detected and labelled post-change; no pre-activation claim is
  made in v0.1.
- Every drift alert supports review, narrow acknowledgement/rebaseline, and history.
- Critical alerts remain available outside the bar when a third-party bar replaces it.
- Signed release verification and clean-VM lifecycle tests pass.
