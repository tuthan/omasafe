# Review — OmaSafe v0.1 implementation

Reviewer: Claude (Opus 5) · Date: 2026-08-20
Scope: `crates/**`, `plugin/**`, `Cargo.toml`, `README.md` at `74df25c` (v0.1 M0–M6)
Verification: git 2.55.0, this machine (Omarchy shell available, 4 third-party plugins
installed). Every finding marked **Confirmed** was reproduced by executing the built
binary against a throwaway `HOME`; the repro is quoted inline.

## Verdict

The architecture is right: CLI-as-engine, thin QML, crate boundaries that match the
identity model, digest-only baselines, bounded reads everywhere, atomic private state
writes, `--no-ext-diff`, symlinks never followed, and a report envelope that keeps
tool version out of source identity. `cargo fmt` is clean and 12 tests pass.

But **the detection engine does not currently detect**, and **the scanner itself is the
most attractive attack surface in the design**. Four defects are individually sufficient
to make a compromised plugin invisible, and all four are reachable by an attacker who
already has exactly the capability OmaSafe exists to catch — write access to a plugin
directory:

1. `plugins inventory` executes arbitrary commands out of a plugin's `.git/config`, and
   the tamper that enables it is excluded from the content digest (C1).
2. Any coverage limitation nulls the content digest, and the null digest then compares
   equal forever — `status` affirmatively prints `unchanged` (C2).
3. Drift alerts fire once per identity, ever. The bar goes green while the drift is
   unresolved, and revert-then-replay is permanently silent (C3).
4. Lost-coverage alerts are unreachable for any plugin without a baseline (C4).

The v0.1 acceptance criteria "Inventory and diff never execute plugin or catalog-controlled
code" and "Every drift alert supports review" are not met, and M5/M6 exits are not met
despite `README.md` and `docs/progress.md` recording M6 as complete (Q9).

Recommendation: treat C1–C4 and H1–H3 as release-blocking, and add the CLI-level
integration tests that would have caught every one of them (Q1) before writing more
features. None of the fixes are large; the gap is test surface, not design.

## Critical

### C1. `plugins inventory` executes plugin-controlled code

`git_metadata()` runs `git status --porcelain` with the plugin directory as cwd
(`crates/omasafe-plugin-trust/src/lib.rs:344`). git honours `core.fsmonitor` from
repo-local `.git/config` and executes it as a command. `GIT_CONFIG_NOSYSTEM=1` does not
prevent this — it only suppresses `/etc/gitconfig`.

The digest cannot see the tamper: `collect_entries()` skips `.git` entirely
(`lib.rs:456`, `lib.rs:476`), so `.git/config`, `.git/hooks/`, and `.git/HEAD` are outside
source identity.

**Confirmed** — read-only inventory, nothing else:

```
git -C $P config core.fsmonitor "/bin/sh -c 'echo PWNED > $HOME/PWNED'"
omasafe-cli plugins inventory   # -> $HOME/PWNED contains PWNED
omasafe-cli plugins status io.example.fsm   # -> "unchanged"
omasafe-cli scan                            # -> "No new actionable changes detected."
```

Impact is amplified by design: the M5 systemd timer and the 5-minute `BarWidget` poll both
call `scan`, which calls `collect()`, so the payload is re-executed unattended, on a
schedule, forever — and OmaSafe reports the plugin clean while doing it.

Recommended action:

- Add a single `git_command()` helper used by *every* git call site
  (`git`, `git_status`, `git_diff`, `run_git_output`, `is_ancestor`) that sets
  `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_SYSTEM=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`,
  `GIT_TERMINAL_PROMPT=0`, `GIT_ALLOW_PROTOCOL=file:git:http:https:ssh`, and passes
  `-c core.fsmonitor=false -c core.hooksPath=/dev/null -c diff.external= -c
  protocol.ext.allow=never -c uploadpack.allowAnySHA1InWant=false --no-optional-locks`.
  Repo-local config must be treated as untrusted plugin content, because it is.
- Include `.git/config`, `.git/HEAD`, `.git/packed-refs`, and the presence/mode of
  `.git/hooks/*` in source identity. Excluding all of `.git` was the right instinct for
  object storage and the wrong one for the trust-relevant files.
- Add a regression test asserting the fsmonitor payload does not run.

### C2. One coverage limitation permanently blinds drift detection, and `status` says "unchanged"

`source_identity()` sets `content_digest: None` whenever `limitations` is non-empty
(`lib.rs:382-386`). Drift comparison is `PartialEq` on the whole struct
(`main.rs:224`, `main.rs:501`). For a non-Git plugin with a limitation, identity reduces to
`(id, repo=None, head=None, tree=None, file_count, limitations)` — none of which change
when file *contents* change.

An attacker triggers this deliberately and cheaply: ship one file over
`MAX_FILE_BYTES` (16 MiB — an ordinary wallpaper, font, or video asset), or a FIFO
("special file skipped"), or an unreadable file, or >10k files.

**Confirmed** — 17 MiB asset, then a real code change:

```
truncate -s 17M $P/assets.bin
echo trust | omasafe-cli plugins trust io.example.big   # digest: null, file_count 2
echo 'Item { Component.onCompleted: evil() }' > $P/main.qml
omasafe-cli plugins status io.example.big   # -> "unchanged"
omasafe-cli scan                            # -> "No new actionable changes detected."
```

This is worse than a missed alert: the tool makes a positive false statement.

Recommended action:

- Always emit a digest over what *was* hashed, and carry coverage separately — e.g.
  `content_digest: Some(..)` plus `covered_files`/`skipped: Vec<SkippedEntry>` where each
  skipped entry contributes its path, mode, size, and skip reason to the hash. Then a
  16 MiB file becomes a *disclosed* gap, not a global off-switch.
- Never let `status` print `unchanged` when coverage is partial. Add a third state
  (`unknown` / `partial`) and make `scan` alert on it.
- Refuse to record a baseline with a null digest unless the user passes an explicit
  acknowledgement flag; today `plugins trust` accepts it silently.

### C3. Drift alerts are one-shot per identity — the bar goes green while the machine is compromised

`scan` keys dedup state on the serialized current identity
(`main.rs:225`) and suppresses any key already present (`main.rs:233`). The key is never
cleared by review, rebaseline, or remediation. Consequences:

- **The badge self-clears.** `BarWidget` polls `scan --format json` every 300 s and
  renders `alertCount`. The second poll returns zero alerts and `quiet: true`, so within
  five minutes of a real, unresolved drift the bar shows `✓` and the panel reads
  "No new actionable changes detected."
- **Revert-and-replay is free.** Detected once, an attacker reverts, re-applies the same
  payload, and is never reported again.
- **A manual scan consumes the notification.** Any `scan` (including the widget's own
  poll and a `--format json` inspection) records the key, so the later
  `scan --notify` from the timer stays quiet. The desktop notification — the channel M5
  requires to work independently of the bar — is racing the bar widget for the only
  delivery.
- Scan state grows without bound, one entry per identity ever seen, each key embedding a
  full identity JSON blob.

**Confirmed**:

```
echo 'evil' > $P/main.qml; omasafe-cli scan   # -> source-drift
echo 'good' > $P/main.qml; omasafe-cli scan   # -> quiet
echo 'evil' > $P/main.qml; omasafe-cli scan   # -> quiet   (same identity as before)
omasafe-cli plugins status io.example.r       # -> "changed"
```

Recommended action:

- Separate the two concepts the code currently conflates. **Outstanding state** =
  "current identity ≠ trusted identity", derived fresh every run, and what the bar and
  panel must render. **Notification dedup** = "have I already told the user about *this*
  outstanding state", and it must be keyed on `(plugin_id, trusted_digest,
  current_digest)` and *cleared* when the plugin returns to its trusted identity or the
  baseline is re-established.
- Give `scan` a `--only-new` flag for the notifier and make the default (widget) path
  report outstanding items without mutating state. A read path must not consume alerts.
- Emit `outstanding` and `new` counts separately in the JSON report and drive the bar off
  `outstanding`.

### C4. Lost-coverage alerts never fire for a plugin without a baseline

`scan`'s loop starts with `let Some(trusted) = ... else { continue };` (`main.rs:212`), so
the `classification == "unscannable"` check below it (`main.rs:241`) is unreachable for
untrusted plugins. A newly installed plugin, a plugin newly replaced by a symlink, and a
plugin whose manifest just became malformed are all silent.

**Confirmed** — a symlinked plugin and a malformed-manifest plugin, no baselines:

```
omasafe-cli plugins inventory   # -> 2 records, both "unscannable"
omasafe-cli scan                # -> "No new actionable changes detected."
```

M5 requires notifying on "missing/unscannable plugin ... or lost coverage" and the
success metric is "a stable machine is quiet; one controlled change produces one alert".
An attacker replacing a plugin directory with a symlink produces zero alerts.

Recommended action: evaluate coverage and provenance checks for every inventoried plugin
before the baseline lookup; only the drift comparison needs a baseline. Also alert on
*newly appearing* plugins — inventory the ID set and diff it against the previous scan.

## High

### H1. A corrupt state file permanently kills the scanner, with the wrong error

`ScanState::load` / `TrustHistory::load` propagate `serde_json::Error`
(`baseline.rs:99`, `baseline.rs:60`). A truncated write (power loss, full disk) leaves
`scan` failing with exit 1 on every subsequent run, including the systemd timer, which
will fail silently forever. `ScanState` reuses `baseline::Error`, so a corrupt
`scan-state.json` reports **"trust history is malformed"** — pointing the user at the
wrong file.

**Confirmed**: `printf 'not json' > scan-state.json; omasafe-cli scan` →
`omasafe: trust history is malformed: expected ident at line 1 column 2`, exit 1.

Recommended action: distinct error types per store; on parse failure rename the file to
`*.corrupt-<timestamp>`, continue with a fresh state, and emit a `lost-coverage` alert
saying so. A dedup cache must never be able to block detection — worst case it re-alerts.
Trust history is different: it must *not* be silently reset, but it should fail with a
recovery instruction naming the actual path, and `review --action restore` should be able
to read the quarantined copy.

### H2. `plugins diff` shows nothing for the two most likely attacks

- **Untracked files are invisible.** `git diff <trusted_head>` covers tracked paths only.
  Adding a new payload file is the obvious move, and the reviewer gets an empty diff under
  a `source_changed=true` header.
- **Non-Git plugins have no review path at all.** `diff` errors with "trusted baseline has
  no Git HEAD". "cloned/local" is a first-class classification in M1, and it has zero
  diff support.

**Confirmed**:

```
echo 'evil payload' > $P/payload.js   # untracked
omasafe-cli plugins status io.example.g   # -> "changed"
omasafe-cli plugins diff io.example.g    # -> "source_changed=true" and an empty diff
```

M4's exit criterion is "source changes remain reviewable even when files are binary,
unsupported, or intentionally obfuscated". Today the criterion fails on plain text.

Recommended action: drive the diff from the collector, not from git. `collect_entries`
already produces `(path, kind, mode, data)` for both sides — emit an added/removed/
modified/mode-changed file list from the trusted-vs-current entry sets (a per-file digest
list in the baseline is enough, and stays digest-only), then use `git diff` purely as an
*enrichment* for tracked text hunks. That fixes untracked files and non-Git plugins in one
change and removes the git dependency from the review path. Add `--untracked-files=all`
plus `--no-renames` in the interim.

### H3. The unattended-trust control is bypassable with a pipe

M3 requires refusing unattended trust without an exact expected identity and an explicit
flag. The interactive branch (`main.rs:132`) reads stdin with no TTY check.

**Confirmed**: `echo trust | omasafe-cli plugins trust io.example.p` records a baseline —
no `--yes`, no expected identity. Any script, wrapper, or `Process` call gets the same
bypass, which also means a compromised plugin's own QML could baseline itself.

Recommended action: require `stdin` and `stderr` to be a TTY (`rustix::termios::isatty` or
`libc::isatty`) for the interactive path; otherwise instruct the caller to use
`--yes --expected-*`. Same check belongs on `review`.

### H4. Marketplace provenance is forgeable, and the validated fetch path is dead code

`fetch_pinned_catalog` — the function that validates hex, pins by commit, checks rollback,
and caches atomically — has **no call sites**. The only reachable path is
`inventory --catalog PATH --catalog-commit STRING` (`main.rs:667`), which:

- accepts any local file as the catalog,
- accepts any string as the commit with no hex/length validation,
- hardcodes `repository: "https://github.com/HANCORE-linux/omarchy-plugin-marketplace"`
  regardless of where the bytes came from.

The report therefore attributes attacker- or user-chosen content to the real registry at a
fabricated revision. `RegistryClaim.registry_repository`/`registry_commit` exist precisely
to bind a claim to an immutable source, and they currently bind it to nothing.

**Confirmed**: `--catalog /tmp/anything.json --catalog-commit "NOT_A_HEX_COMMIT; rm -rf /"`
is accepted and emitted into the report.

Recommended action: wire `fetch_pinned_catalog` behind a `marketplace refresh` subcommand
and make it the normal path. Keep `--catalog` for fixtures only, but require
`--catalog-repository` alongside it and label the snapshot `source: "local-file"` in the
report so a fixture can never masquerade as the registry. Validate the commit as exactly
40 or 64 hex chars everywhere (see M10).

### H5. Catalog parsing fails open

`CatalogDocument::Wrapped` has all-`Option` fields, so **any** JSON object deserializes
successfully with zero entries. Every plugin is then reported `unlisted` with no error —
the fail-open answer to a security-relevant question.

**Confirmed**: `{"pluginList":[{"id":"io.example.widget",...}]}` parses fine, produces
`status: "unlisted"`, `reason: "no catalog entry matched the plugin ID"`, exit 0.

Also: `load_catalog` calls `fs::read` before the `MAX_CATALOG_BYTES` check, so the limit
does not bound memory — a large or crafted file is fully read first. Same for the
unbounded `git show` output in `fetch_pinned_catalog`, and for `query_shell`'s
`Command::output()`.

Recommended action: reject a document that matches neither a top-level array nor an object
containing `entries`/`plugins` (deny-unknown-shape, not `unwrap_or_default`), and treat an
empty entry list from a non-empty file as an error. Check `fs::metadata().len()` before
reading, and read through `Read::take(MAX + 1)` so the bound is real.

### H6. Free-text limitation strings are part of source identity

`SourceIdentity.limitations` is populated from `PluginRecord.reason` (`main.rs:110`,
`main.rs:222`, `main.rs:622`) and participates in `PartialEq`. `reason` carries
environment-dependent English: "Git working-tree status is unavailable", "file unreadable
`{path}`: Permission denied", "metadata unavailable: …". So a transient `git` failure or a
permissions change produces a **false drift alert**, and rewording any message string
invalidates every baseline.

That is the exact failure mode M3's exit criterion forbids ("timestamps, tool version,
**message wording** … do not change source identity") and that success metric 4 measures
("Zero alerts when only OmaSafe tool/message versions change").

Recommended action: replace the string with a stable, sorted set of typed codes
(`enum LimitationCode { OversizeFile, UnreadableFile, SpecialFile, FileLimit, ByteLimit,
GitStatusUnavailable, … }`), keep human text in a separate non-identity field, and
exclude anything path- or errno-derived from the hash input.

## Medium

- **M1. `valid_ref` permits a leading `-`.** `lib.rs:428` allows `-`, and the
  `ref_b == "WORKTREE"` branch passes `ref_a` as its own argv element. `--ext-diff` placed
  after the hardcoded `--no-ext-diff` wins and re-enables repo-local `diff.external`
  — **confirmed executing** `/bin/sh` from `.git/config`. Today the CLI is saved only
  incidentally: `diff`'s range parser drops any arg starting with `--`
  (`main.rs:544`), so `--ext-diff..WORKTREE` never reaches git. That is a coincidence
  standing between a `pub fn` and command execution, and `=` being absent from the allowed
  byte set is the only thing blocking `--output=<path>` file truncation (verified that
  `git diff --output=FILE` creates the file). Add `--end-of-options` before the refs and
  reject any ref beginning with `-`.
- **M2. Plugin root ignores `XDG_CONFIG_HOME`.** `home()?.join(".config/omarchy/plugins")`
  is hardcoded at four call sites, while `schedule_install` honours `XDG_CONFIG_HOME`
  (`main.rs:348`). On a machine with a relocated config home, OmaSafe scans an empty path.
  Add `--plugin-root` (also the missing hook that makes CLI integration tests possible —
  see Q1) and route it through `XdgPaths`.
- **M3. 41 false coverage limitations on a stock machine, and the real provenance field is
  ignored.** Built-in plugins are reported by `omarchy plugin list --json` but do not live
  in `~/.config/omarchy/plugins`, so every run emits 41× "shell reports plugin X but its
  directory was not found" (verified on this machine). `scan` papers over it with a
  `starts_with("shell reports plugin ")` string filter (`main.rs:292`) — string-typed
  control flow guarding a security decision. Separately, the real shell output carries
  `clonedFrom` (`""` for built-ins, the clone URL otherwise), which `ShellPlugin` does not
  deserialize. The plan's premise that "Omarchy's list output omits" the repository URL is
  wrong; `clonedFrom` is both the built-in discriminator and the repository source, and it
  would remove the `name.starts_with("omarchy.")` heuristic at `lib.rs:252`.
- **M4. Shell↔directory reconciliation is keyed on directory name.**
  `shell_by_id.remove(&name)` (`lib.rs:130`) uses the directory name while the record ID
  comes from the manifest (`lib.rs:243`). Any plugin whose directory name differs from its
  manifest ID loses all shell metadata (`enabled`/`active`/`firstParty` become `null`) and
  additionally produces a false "directory was not found" limitation. Match on manifest ID
  with directory name as fallback, and report a mismatch as its own finding — a directory
  name that disagrees with the manifest ID is itself a signal.
- **M5. `review` decisions are recorded and never consulted.** `acknowledge` and `exclude`
  append to `history.decisions` (`main.rs:479`) and nothing reads that field. Acknowledged
  drift is not represented anywhere in `scan` or `status`, and scoped exclusions do not
  scope anything. `exclude`'s guard is one string comparison against `"plugin"`
  (`main.rs:441`), so `--scope "plugin "` passes. Either implement the semantics or drop
  the subcommand from v0.1 — a recorded-but-inert security control is worse than an absent
  one, and M4 explicitly requires "never make 'accept revision' equivalent to 'ignore
  future changes'".
- **M6. `restore` picks "the one before the last" and appends.** `nth(1)` on the reversed
  history (`main.rs:455`) means repeated restores toggle between two baselines, and nothing
  is previewed or confirmed before a baseline is replaced. Make it explicit:
  `restore --to <index|digest>`, print the identity, require confirmation.
- **M7. State durability and concurrency.** `write_atomic` never fsyncs the temp file or
  the parent directory, so `rename` can land with unflushed content — the exact scenario
  H1 turns into a permanent outage. There is no locking, so a concurrent `trust` and
  `scan` (likely, given the 5-minute widget poll) is a lost-update race on
  `trust-history.json`: both read, both write, one baseline vanishes. Add `File::sync_all`
  on the temp file plus a parent-dir sync, and take an advisory lock (`flock`) around
  read-modify-write. Cap or compact `scan-state.json`.
- **M8. Attacker-controlled strings reach the terminal and the notification server
  unsanitized.** Plugin IDs come from the plugin's own `manifest.json`, and repository URLs
  from `git config --get remote.origin.url` — both are printed raw in text mode
  (`main.rs:707-717`, `main.rs:327`) and passed as the `notify-send` body
  (`main.rs:334`). ANSI escapes in an ID can rewrite the preceding line of a security
  report; several notification servers interpret markup in the body. Escape control
  characters on output, reject IDs that are not `[A-Za-z0-9._-]`, and pass
  `--hint=string:x-canonical-private-synchronous:` style metadata rather than trusting the
  body.
- **M9. `schedule_install` hardening.** `ExecStart={}` interpolates
  `current_exe()` unquoted and unescaped (`main.rs:357`); systemd treats `%` as a specifier
  and splits on whitespace, so a path containing either yields a broken or altered unit.
  Existing units are overwritten without diffing or confirmation. There is no
  `RandomizedDelaySeconds`, no `ProtectSystem`/`PrivateTmp`/`NoNewPrivileges`, and no
  `AssertPathExists`. Also, `notify-send` from a user timer needs
  `DBUS_SESSION_BUS_ADDRESS`, which is not reliably present — M5 requires the notification
  to arrive independently of the bar, so this needs explicit verification (or
  `systemd-notify`/`After=graphical-session.target` plus an environment import) and a
  fallback that records undelivered alerts in state.
- **M10. `fetch_pinned_catalog` input validation (dead today, will not stay dead).**
  Accepts 1–64 hex characters, so an abbreviated prefix passes as an "immutable commit" —
  require exactly 40 or 64. `repository_url` goes unvalidated into `git remote add`
  (`lib.rs:182`): a `-`-prefixed value is argv injection and an `ext::` URL is direct
  command execution — restrict to `https://` and reject leading `-`. `repository_dir
  .to_str().unwrap_or_default()` (`lib.rs:178`) silently passes `""` to `git init --bare`
  on non-UTF-8 paths; return an error instead. The rollback check is skipped entirely when
  `catalog.meta.json` is unreadable or unparseable (`lib.rs:193`) — a rollback guard that
  an attacker disables by deleting one file should fail closed.
- **M11. `scan` coverage gaps vs M5.** No marketplace correlation at all, so
  "conflicting provenance" is never alerted. `non_builtin_bar_replaces_bar` is computed
  and never surfaced outside the inventory JSON. `active_full_bar` is silently
  last-write-wins when multiple active bar plugins exist (`lib.rs:113` then `lib.rs:133`)
  instead of being reported as a conflict. And there is no distinct exit code for
  "drift found", which any scheduled consumer needs — reserve `0` quiet, `1` error,
  `2` usage, `3` alerts outstanding.
- **M12. The bar widget is broken and over-reassuring.** `Process` and `StdioCollector`
  are used with no `import Quickshell.Io` (`BarWidget.qml:34-40`) — the component will not
  instantiate. `runScan()` is never called on load, so the first 300 s show a state that
  was never measured. Most importantly `text: root.alertCount > 0 ? "!" : "✓"` renders
  `scanState === "unavailable"` as a **green check** — CLI failure is indistinguishable
  from all-clear, which is the one thing a trust indicator must never do. `Panel.qml`
  binds `open: root.opened` to a property the file never declares, and shows none of the
  M6-required content (installed identity, marketplace correlation, baseline, changed
  files, cache age, coverage limitations, "replaces the bar"). Add a distinct
  unknown/unavailable glyph, scan on load, and render the coverage block.

## Quality

- **Q1. Test coverage is the root cause, not a side note.** 12 tests, all at library level,
  **zero** covering the CLI — and every C- and H-level finding above lives in
  `main.rs` or in the interaction between `main.rs` and the libraries. The plan's own test
  matrix is largely unimplemented: mode-only changes, `MAX_FILES`/`MAX_TOTAL_BYTES`,
  digest suppression, malformed UTF-8 paths, special files, catalog rollback,
  `fetch_pinned_catalog` (untested in full), concurrent scans, interrupted/corrupt state,
  baseline recovery, notification dedup, acknowledge/exclude, trust rollback, backup
  directories, detached HEAD, third-party full bars. The tests that exist are also not
  hermetic: they shell out to real `git` without `GIT_CONFIG_GLOBAL=/dev/null`, so a
  developer with `commit.gpgsign=true` or a global `core.hooksPath` fails the suite; temp
  dirs are hand-rolled from `SystemTime` nanos and leak on any failing assert. Add
  `tempfile` as a dev-dependency, add `assert_cmd`/`insta` CLI tests driven by
  `--plugin-root` (M2), and isolate git env in fixtures.
- **Q2. No CI, despite M0's exit criterion** ("CI runs unit tests and a repeatable smoke
  workflow"). No `.github/`, no `rust-toolchain.toml`, no documented MSRV while using
  `edition = "2024"`. Add fmt + clippy `-D warnings` + test on stable, and pin the
  toolchain.
- **Q3. Every single-plugin command hashes every plugin.** `trust`, `status`, `diff`, and
  `scan` all call `collect()`, which reads and SHA-256s up to 64 MiB across *all* plugins
  including built-ins, to then `.find()` one ID. The widget does this every 300 s
  indefinitely — measurable battery cost for no benefit. Add `collect_one(root, id)`, or
  make digesting lazy per record.
- **Q4. CLI surface.** ~150 lines of hand-rolled `while index < args.len()` parsing
  duplicated across four subcommands, with divergent behaviour: `--format json` everywhere
  except `diff`, which only honours `--format=json` (`main.rs:574`) and **silently ignores
  every unknown argument** while the other three error. `--format` also happily consumes
  the next flag as its value. The `[command] if command == "scan"` arm (`main.rs:44`) is
  dead — the following arm already matches. `classification`, `status`, `action`, and
  `kind` are stringly typed and compared by literal across crate boundaries
  (`"unscannable"`, `"Git-managed"`, `"bar"`), which is how M3's prefix-matching hack
  became possible. Move to `clap` derive and enums; it removes code and closes the
  inconsistencies.
- **Q5. Timestamps.** `now()` returns Unix epoch **seconds as a string**, and `"0"` if the
  clock is before the epoch (`main.rs:740`). This lands in `Report.generated_at`,
  `accepted_at`, `created_at`, and the catalog's `retrieved_at` — all of which the plan
  describes as human-visible age/generation information. Use RFC 3339 (`jiff` or
  `time`), and keep a numeric epoch field separately if the QML needs to compute age.
- **Q6. Schema versions are written and never checked.** `TrustHistory::schema_version` and
  `ScanState::schema_version` are set on write and ignored on load, so a future format
  loads as garbage rather than failing cleanly, and `serde(default)` fills missing fields
  silently. `SCHEMA_VERSION` in `omasafe-report` is a string constant not tied to either.
  Validate on load and reject unknown majors with an actionable message.
- **Q7. Small correctness/consistency items.**
  4 clippy warnings (`comparison_to_empty` at `main.rs:265`, `collapsible_if` ×2,
  `unnecessary_map_or` at `lib.rs:251`) — clippy is not in CI, so these will accumulate.
  State/config/cache directories are created 0755 (`paths.rs:27`) while the files inside
  are deliberately 0600; make the directories 0700. `write_atomic` writes then chmods,
  leaving a window where the file is 0644 — create with
  `OpenOptions::new().mode(0o600)` instead. `sha2` is duplicated in two crate manifests
  instead of `[workspace.dependencies]`. `Cargo.toml`'s `repository` uses an SSH remote
  (`git@github.com:tuthan/omasafe.git`) where crates.io/tooling expects an HTTPS URL.

### N2. High — the C2 fix removed the I/O bound that `MAX_FILE_BYTES` existed to provide

`skipped_file_digest` (`lib.rs:~640`) streams the **entire** over-limit file through

`size ‖ first 1 MiB ‖ last 1 MiB` for over-limit files (detects realistic tampering,

remainder as a disclosed gap. Then add the regression test that asserts scan wall-time is

straight into memory on every scan. Apply `MAX_FILE_BYTES` and the aggregate budget here
too. (`packed-refs` on a large repo is legitimately multi-MB, so pick the cap deliberately.)

### N5. Medium — a `.git` **file** is excluded from identity while git still runs in it

`collect_entries` only calls `collect_git_metadata` when the `.git` entry `is_dir()`, but
`has_git()` (`lib.rs:292`) returns true for a `.git` *file* as well. For a gitlink or
linked worktree, OmaSafe runs git commands against a `gitdir:` target it never hashes — so
the pointer itself, and the real config behind it, are outside source identity. Hash the
`.git` file's contents, and either follow the `gitdir:` to hash the config there or record
`gitlink_uncovered` as a limitation.

### N7. Low–Medium — `--notify` now silently means "only-new mode"

The read/write split is the right fix, but it is expressed by overloading the notification
flag: `--notify` both delivers desktop alerts and switches `alerts`/`quiet` from
"outstanding" to "new". So the timer's JSON reports `quiet: true` while drift is
outstanding, and a caller cannot ask for both views. Split the concerns —
`--only-new` for dedup, `--notify` for delivery — and emit `outstanding` and `new` counts
side by side in `ScanResult` so the widget renders outstanding and the notifier consumes
new. Three dedup idioms now coexist in one function (N1, N6); one helper should own it.

### N8. Low — `limitations` is order-dependent while `entries` is sorted

Observed: `["oversize_file", "oversize_file", "special_file"]` — stable on this filesystem
across five runs, but readdir order is unspecified, so a rename or re-create that reorders
directory entries flips the vector and produces false drift. Sort and dedup before it
enters identity (keep counts if the count is wanted, but derive them deterministically).

### N9. Low — corrupt-state diagnostics

## New — introduced by this pass

### R1. High — adding `file_digests` to the identity invalidates every existing baseline

`SourceIdentity` gained `file_digests`, it participates in the derived `PartialEq`, and
`HISTORY_SCHEMA_VERSION` was left at `1`. `#[serde(default)]` means an existing
`trust-history.json` loads *successfully* with an empty map, which then compares unequal to
a freshly collected identity — so every baseline recorded before this change reports drift
on byte-identical source.

**Confirmed** — hand-written pre-`file_digests` history, source untouched:

```
plugins status  -> io.example.p: changed
scan            -> source-drift: installed source differs from the trusted baseline
```

This breaks the v0.1 acceptance criterion "Unchanged source remains unchanged across an
OmaSafe version bump", and success metric 4 ("zero alerts when only OmaSafe versions
change"). It is also precisely what the `schema_version` check added in this same pass
exists to catch — the version just was not bumped.

Recommended action: keep `file_digests` out of the drift decision. It is derived review
data — `content_digest` already covers every byte it covers — so a hand-written `PartialEq`
(or a `fn matches(&self, other) -> bool` used by `scan`/`status`) that compares
`plugin_id`, `repository`, `head`, `tree`, `content_digest`, `file_count`, and
`limitations` fixes the migration and R6 at once. If it must stay in the comparison, bump
the schema version and migrate: treat a v1 record's absent map as "not recorded" and skip
that field for that record.

### R2. High — the N2 fix reopened C2 through the aggregate limit

Two changes combined badly: over-limit files now add their **full length** to
`total_bytes`, and the aggregate-limit branch still `return`s, aborting the traversal. So
one ordinary large asset exhausts the 64 MiB budget and everything visited afterwards is
dropped from source identity entirely.

**Confirmed** — plugin with a 100 MiB asset, `manifest.json`, and eight `.qml` files:

```
file_count: 2 of 10 real files
covered:    ['asset.bin', 'code_h.qml']
limitations: ['aggregate_byte_limit', 'oversize_file']

tamper each source file:
  code_a..code_g.qml -> *** MISSED ***
  code_h.qml         -> detected
```

Seven of eight source files became invisible to drift detection. Which ones survive
depends on `fs::read_dir` order (tmpfs returns reverse-creation order here), so coverage is
nondeterministic across filesystems and re-creations — and an attacker who can drop a large
file into the directory chooses what stops being watched.

A plugin shipping a 100 MiB video, model, or font pack is completely ordinary, so this
fires by accident too.

Recommended action: `continue` instead of `return` on the aggregate limit, so every
remaining path still gets a `kind: b'x'` entry (for files under 1 MiB `skipped_file_digest`
hashes the full content anyway, so most coverage survives). Count only bytes actually read
against the budget — an over-limit file consumes ≤2 MiB, not its full length. And sort
directory entries before recursing so coverage is deterministic regardless of filesystem.

### R3. High — the new lock file is a permanent brick, and does not fix the race it targets

`acquire_lock` uses `OpenOptions::create_new(true)` with no PID, no staleness check, no
timeout, and no retry. Any SIGKILL, OOM kill, or power loss between acquire and `Drop`
leaves the lock behind, and **every subsequent state write fails forever**.

**Confirmed** — `touch trust-history.lock`, then:

```
plugins trust …  -> omasafe: trust history I/O error: File exists (os error 17)   exit 1
scan --notify    -> omasafe: trust history I/O error: File exists (os error 17)   exit 1
```

The scheduled timer then fails silently and permanently, and the message names no file and
no remedy. That is strictly worse than the unlocked version it replaced.

It also does not close the M7 race. The lock is taken inside `write_atomic`, while
`TrustHistory::load` runs outside it — so two concurrent `trust` invocations both load,
both write (serialized), and the second discards the first's record. The lost update
survives.

Recommended action: use `flock(2)` (`rustix::fs::flock`, or `fs2`) on the state file
itself, held across load → mutate → write. The kernel releases advisory locks when the
process dies, so staleness is structurally impossible, and it actually covers the
read-modify-write window. Less code than the current approach.

## Medium

- **R4. Mode-only changes are reported as "something changed, nothing to see".**
  `file_digests` hashes `entry.data` only — not `mode`, not `kind`. Confirmed: `chmod +x`
  on a bundled script gives `status: changed` and `diff` → `source_changed=true` with an

## New

### U1. Medium-High — the widget reads exit code 3 as "unavailable"

`plugin/BarWidget.qml:48` is unchanged:

```qml
onExited: function(exitCode) {
  if (exitCode !== 0) root.scanState = "unavailable"
}
```

Exit 3 now means "findings outstanding", and `has_outstanding` is driven by `live_keys`, so
the widget's own `scan --format json` (no `--only-new`) returns 3 whenever anything is
outstanding. `StdioCollector.onStreamFinished` fires before `onExited`, so `applyScan`
correctly sets `attention` and then `onExited` overwrites it with `unavailable`.

Net effect: the button renders **`?`** exactly when there is something to report, while
`tooltipText` — still keyed off `alertCount` — simultaneously says "N item(s) need review".
This is round 2's M12 inverted: failure used to look like all-clear, and now drift looks
like failure. The new `outstandingCount`/`newCount`/`alerts` properties added in the same
change are populated but cannot be trusted to drive the glyph.

Recommended action: treat 0 and 3 as success and only escalate on other non-zero codes —
`if (exitCode !== 0 && exitCode !== 3) root.scanState = "unavailable"`. Better, key the
glyph off `outstandingCount` and reserve `?` for a parse failure or a genuinely unexpected
exit code, so the three states (clear / findings / unavailable) each have exactly one
source of truth.

### U2. Medium — the systemd unit has no `SuccessExitStatus=3`

`schedule_install` still writes a bare `Type=oneshot` service, so exit 3 marks
`omasafe-scan.service` failed. And because the exit code follows `live_keys` (outstanding)
rather than `alerts` (new), the `--notify --only-new` timer invocation returns 3 even when
it printed nothing:

```
timer invocation:   exit 3
timer, nothing new: exit 3
```

So the unit enters a permanently failed state for as long as any finding is unresolved —
which is the normal steady state this tool is designed to produce. `systemctl --user status`
and the journal will show a failing timer while OmaSafe is working exactly as intended,
which is the fastest way to get a user to disable it.

Recommended action: add `SuccessExitStatus=3` to the generated unit. Separately, decide
deliberately whether `--only-new` should also scope the exit code to new findings — a
notifier that reports "nothing new" and exits non-zero is arguably wrong regardless of the
unit setting.

### U3. Medium — `collect_one` exists but saves no work

`collect_internal` applies the target filter *after* `inspect_plugin`, and `inspect_plugin`
is what calls `source_identity()` — the read-and-hash of every file. The filter therefore
skips only the `Vec::push`.

**Measured** — 12 plugins × 40 × 200 KB files:

```
plugins status io.p1   2.845s
plugins inventory      2.806s
```

Identical, so Q3 is unchanged in effect: every single-plugin command still hashes the whole
plugin root, and the widget's 5-minute poll still pays for all of it.

Recommended action: hoist the check above `inspect_plugin`. `manifest_id(&path)` is already
computed a few lines earlier for the shell-key logic, so the guard is nearly free:

```rust
if let Some(target_id) = target_id
    && manifest_id.as_deref() != Some(target_id)
    && name != target_id
{
    continue;
}
```

One edge case to preserve: when the manifest is unreadable, `record.id` falls back to the
*shell* plugin ID, so a target that matches only that would be missed by the hoisted
check — resolve `shell_plugin` first (it is also already available) and include its ID in
the comparison.

### U4. Low — lock ergonomics

The lock file is still created at 0644 while the state it guards is 0600. Lock contention
surfaces as `trust history I/O error: state lock is busy; retry later` even when the
contended file is `scan-state.json`, and it is a hard exit 1 — so the widget's 5-minute poll
racing the daily timer will occasionally render `unavailable`. Consider a longer retry
window for read-mostly paths, or treating contention as "skip this tick" rather than an
error.

## Closing assessment

Seven rounds, and the v0.1 implementation now holds up under adversarial testing. The
findings that mattered are closed and independently re-verified:

- **No code execution from plugin content.** The `core.fsmonitor` path is dead, all git
  invocations run through one hardened constructor in `omasafe-core`, and `.git/config`,
  `HEAD`, `packed-refs` and hook contents are inside source identity — so the tamper that
  enabled it is itself detected.
- **No silent detection gaps.** Digests survive partial coverage; over-limit files are
  sampled at bounded cost with the gap disclosed; coverage alerts fire without a baseline;
  alert dedup clears on recovery so revert-and-replay and repeated history rewrites each
  re-alert; and losing the trust history raises its own alert rather than going quiet.
- **State is durable and honest.** `flock` held across load→mutate→write with no lost
  updates, fsynced atomic writes, 0600 files in 0700 directories, schema validation, and
  corrupt files quarantined rather than fatal.
- **The review path works** for untracked files, non-Git plugins, and mode-only changes —
  the three cases that previously showed "something changed" and nothing else.
- **Provenance is commit-bound and refuses to overclaim.** An unverified cache is labelled
  `unverified-cache`, stale snapshots are disclosed, and registry claims never suppress a
  local signal.
- **Output cannot lie to the reviewer.** Control characters from plugin-controlled names are
  escaped on every text path.

The engineering discipline over these rounds is worth noting: each round fixed everything
raised, and the failure mode moved steadily outward — from critical detection defects in
rounds 1–3, to fixes whose consequences weren't followed into consumers in rounds 4–6, to
nothing in round 7. The CLI test suite grew from zero to ten hermetic cases pinning exactly
the regressions that had been slipping through, which is what made the last two rounds
converge.

Remaining risk is concentrated where the docs say it is: the desktop surface has never run
on a real Omarchy system, and M7 packaging and signing are untouched. Those are the v0.1
release gate, not correctness debt.
